# PHPバージョンアップ対応

あなたは経験豊富なソフトウェアエンジニアです。Rector等による機械置換済み、または未着手のPHPコードベースを対象に、指定バージョン間の互換性を体系的に検証・修正します。

## 背景・設計思想

PHPのメジャー/マイナーバージョンアップは、単純な構文置換（Rectorの`LevelSetList`実行など）だけでは**修正漏れ・過剰変換の両方**が発生します。

- **修正漏れ**: 機械置換ツールは「未定義配列キーへの直接アクセス」「null を内部関数へ渡す」等、静的にコンパイル時点では判定しづらい意味論的な問題を見逃す。
- **過剰変換**: `LevelSetList::UP_TO_PHP_83` のような「バージョン上限指定」の機械置換ルールセットは、**指定した上限のPHPバージョンで初めて使える構文へのアップグレード**まで行うことがある。これは「新しいバージョンでは動く」が「移行期間中に並走させる旧バージョンではパースエラーになる」という本番障害に直結する。

このスキルは、上記2種類の問題を「静的（機械網羅）→ レビュー（意味論）→ 実行時（動的網羅）」の3層防御で潰すことを目的とする。単一の手法（Rectorだけ、テストだけ等）に依存しない。

`--keep-compat` の on/off で切り替わるのは、**「新構文への変換を許すか否か」の1点のみ**である。それ以外のフェーズ——未定義キー/プロパティアクセスの重大度格上げ、null引数・暗黙型変換の副作用、ネイティブクラス継承のメソッド衝突、外部通信ラッパーのエラー型対応——は、`--keep-compat` の指定有無にかかわらず**常時実施**する。すなわちこのスキルの大半は完全移行・並走運用のどちらでも共通の作業である。

さらに、`--keep-compat` 未指定の**完全移行（既定パス）では、本命リスクが構文互換から「依存パッケージのメジャーバンプに伴うAPI破壊」へ入れ替わる**。並走運用（keep-compat 指定）で最優先だった「下位互換破壊構文の差し戻し」の重みが消える代わりに、依存メジャーバンプ由来のメソッド削除・リネーム（`gte()`→`greaterThanOrEquals()` 級）の突合が主戦場になる（`references/breaking-changes.md` §6）。

## 引数の解釈

引数はすべて任意であり、`--key=value` 形式に統一されている。位置引数は無い。

- **`--target-paths=<paths>`**: 検証・修正対象のパス。複数はカンマ（`,`）区切り（例: `--target-paths=wp-content/plugins/my-plugin,wp-content/themes/my-theme`）。グロブ可。相対パスは**gitリポジトリのルート基準**で解決する（スキルを起動したディレクトリ基準ではない）。空白を含むパスやグロブは値全体をシングルクォートで囲む。**バッククォートは使わない**——シェルのコマンド置換として解釈され、意図しないコマンドが実行されうる。
  - **省略時はgitリポジトリのルート配下全体**（`git rev-parse --show-toplevel`）を対象とする。これが既定であり、ユーザーへの確認は行わない。
  - **指定はフェーズ3のスコープ原則を無効化しない**。`--target-paths` が定めるのは解析スコープの外枠だけであり、そのスコープ内では引き続き denylist（全ファイルを候補に置き、除外するファイルは除外理由を記録する）で進める。**「パスを指定できる＝絞り込んでよい」ではない。**
  - 除外パスは、フェーズ1（PHPStan/PHPCompatibility）およびフェーズ2（Rector の `withSkip()`）の除外設定と**完全一致**させる。ここで独自の除外を定義しない（定義が3箇所目になると必ずズレる）。
- **`--from=<version>`**: 移行元PHPバージョン（例: `7.4`）。省略時はユーザーに確認する。
- **`--to=<version>`**: 移行先PHPバージョン（例: `8.3`）。省略時はユーザーに確認する。
- **`--keep-compat` 未指定（既定・主線）**: `--to`バージョンへの**完全移行**として進める。下位バージョンとの並走を考慮せず、新構文への変換もそのまま許容してよい。この既定パスでは本命リスクが構文互換から**依存パッケージのメジャーバンプに伴うAPI破壊**（`references/breaking-changes.md` §6）へ入れ替わる点に注意する。多くの移行はこちらに該当する。
- **`--keep-compat=<version>`（並走期間がある場合の例外オプション）**: **移行後も動作を維持すべき下位バージョン**（例: `7.4`）を指定する。本番デプロイとサーバー側のPHPバージョン切替（ホスティングの管理画面等での切替）が並走する時間帯があるなど、「新バージョンでは動くが、切替完了までは旧バージョンでも動かなければならない」制約がある場合にのみ指定する例外的な運用。
  - 指定時は、下位互換を破壊する構文（第一級callable `(...)` 、`never`/`readonly`/`enum`/コンストラクタプロパティ昇格 等、`--from`より新しいバージョンでしか使えない構文）への変換を**禁止**し、検出時は下位互換な書き方へ差し戻す。
  - 詳細は `references/breaking-changes.md` の「バージョン別・構文レベルの破壊的変更」を参照。

`--target-paths` が想定外だった場合の扱い。**いずれも黙って既定値へフォールバックしない**（フェーズ4の「フォールバック値は捏造しない」と同型の考え方である）。

| 状況 | 振る舞い |
|---|---|
| 省略、かつgitリポジトリでない | gitルートを取得できない旨を伝え、**対象パスをユーザーに確認する**。カレントディレクトリを黙って起点にしない（意図しない広範囲の走査を防ぐ） |
| 値が空（`--target-paths=` / `--target-paths=,,`） | 指定ミスとして扱い、ユーザーに確認する。省略時の既定へ落とさない |
| 指定したパスが存在しない | 存在しないパスを明示して報告する。カレントディレクトリ基準なら存在する場合はその旨を提示し、どちらを意図したか確認する |
| グロブが1件もマッチしない | 上と同様に報告する。**0件のまま進めない**——「問題なし」と誤報告する最悪の失敗になる |
| 旧形式（位置引数）で呼ばれた | `--target-paths=` 形式へ変わったことを伝え、新形式を提示する。**推測して勝手に解釈しない**（後方互換は設けていない） |

## 手順

### フェーズ0: ブランチ準備

1. 対象リポジトリの現在のブランチ状態を確認する（`git status`）。未コミットの変更があればユーザーに確認する。
2. 作業ブランチを作成する（ベースブランチ・命名規則はユーザーに確認、または既存の命名規則に従う）。
3. **対象ブランチが既に機械置換・依存更新済みでないかを先に確認する**。「別ブランチをこれからマージする」という前提で作業を始める前に、対象ブランチ自身の `git log` を確認すること。過去に一度、機械置換ブランチが対象ブランチへ既にマージ済みだったにもかかわらず「まだ未マージ」という前提で計画を立ててしまい、方針の立て直しが必要になった実例がある。特に複数ブランチ（本番系・開発系等）が並行して存在するプロジェクトでは、ブランチごとに移行の進み具合・方針（後述の`--keep-compat`要否や、依存メジャーバンプの実施有無）が異なることがあるため、**ブランチごとに現状を実地確認してから計画する**。
4. **機械置換（Rector）の適用状況で分岐する**:
   - **未適用（対象ブランチにRectorがまだ入っていない。dev ブランチ等をゼロから移行する場合）**: 自分で実行する → **フェーズ2「Rector 機械置換の実行」**へ進む。
   - **別ブランチで適用済み・未取り込み**: そのブランチを作業ブランチへマージする（フェーズ2はスキップ可）。マージ時は以下に注意する。
   - マージ前に、機械置換ブランチの分岐元とベースブランチの現在のHEADの関係を必ず確認する（`git merge-base --is-ancestor` 等）。分岐後にベース側へ機能追加コミットが積まれている場合、マージ時に衝突する可能性がある。衝突時は「機能追加はベース側を採用し、バージョン対応の差分（型キャスト等）を手動で再適用する」方針を基本とする。
   - **vendor/依存関係の扱いは方針で分岐する**: `--keep-compat` 未指定の**完全移行では、依存パッケージのメジャーバンプが標準工程**になる（下位バージョン制約が外れるため、対象PHPバージョンに最適化された最新メジャーへ揃えるのが自然。ネイティブクラス継承衝突（§5）の解消も依存更新で片づくことが多い）。一方、**依存を据え置く（メジャーバンプしない）のは主に `--keep-compat` 指定時の選択肢**——並走する旧バージョンでも動くバージョンに固定し続ける必要がある場合。機械置換ブランチが `composer.json` の依存メジャーバージョンも同時に引き上げている場合、完全移行ならそのまま取り込むのが基本、据え置き方針なら分離する。いずれにせよ依存メジャーバンプは影響範囲が広く（API変更・データ処理の回帰リスク。詳細は `references/breaking-changes.md` §6）、取り込む場合はフェーズ3で依存側API破壊の突合を必ず行う。
   - 複数ブランチを扱うプロジェクトでは、ブランチによって「並走期間があり`--keep-compat`が必要」「単独で完全移行してよく依存メジャーバンプも許容」等、方針そのものが異なりうる。一方のブランチ向けに決めた方針をそのまま他方へ適用しない。
5. **複数ブランチを並行して移行する場合、修正の適用状況をブランチ間で突き合わせ続ける**。方針（`--keep-compat`の要否等）が違っても、**カテゴリ3以降の実バグ修正はどのブランチにも等しく必要**である。片方で見つけた不具合は、他方にも同型が残っていないか毎回確認する。
   - **突合の方式を固定する**: `git diff <a> <b> -- <src> ':(exclude)vendor'` の**全ハンクを1件ずつ**「意図した方針差」「適用漏れ」へ分類する。**両ブランチで静的解析を再実行して結果を比べる方式は採らない** —— 再実行方式は「両方で同じように検出されない欠陥」を構造的に見逃す。
   - **双方向で行う**（a→b と b→a）。片方向だけだと「b にあって a に無い」修正が漏れる。
   - 成果物は台帳として残す（`references/triage-ledger.md` §4）。**ゲートは「全ハンク数 == 台帳の行数」かつ「分類の未記入 0 件」。**
6. **同一の作業ディレクトリで方針の異なるブランチを切り替えない**。`vendor/` をコミットするブランチと `.gitignore` するブランチが混在すると、切替時にgitが追跡ファイル（`vendor/autoload.php` を含む）を削除し、**サイトが全リクエストFatalになる**。実例あり。方針をブランチ間で統一するか、`git worktree` でブランチごとに作業ディレクトリを分ける。

### フェーズ1: 静的解析セットアップ

1. 静的解析ツールを導入する（アプリ本体のcomposer.jsonではなく、独立した開発ツール用composer環境に導入することを推奨。本番へのデプロイ対象に混入させない）。
   - **PHPCompatibility**（`squizlabs/php_codesniffer` + `phpcompatibility/php-compatibility`）: `--keep-compat` 指定時は `testVersion` を `<keep-compat>-<to>`（例: `7.4-8.3`）とする。**守備範囲は「削除・非推奨になった関数/定数/構文の呼び出しの有無」だけ**であり、値の型・実行経路は一切見ない。**「ERROR 0件」を合格ラインにしてはならない** —— 導入版が削除 API を ERROR ではなく WARNING としか報告しない場合、終了コードは常に 0 になる。採否は `scripts/verify-gate.sh --gate=phpcompat` の3値判定で決める（`references/detection-gates.md` §4）。
   - **PHPStan**（+ フレームワーク固有拡張。WordPressなら `szepeviktor/phpstan-wordpress`）: `phpVersion` を `--to` の値に設定。**そのPHPStanバージョンの最大 level を必達とする**（数値を直書きせず、導入時に確認する）。level を下げて逃げない。
     - **判定は identifier ホワイトリストで行う**（`scripts/php8-identifiers.txt`）。level を上げると PHP バージョンと無関係なノイズが混ざるが、**対策は「level を下げる」ではなく「level は最大にし、判定対象を identifier で絞る」**である。ノイズ分離の3方式と禁止事項は `references/detection-gates.md` §3。
     - **PHP バージョン起因の identifier を `ignoreErrors` / baseline へ入れてはならない。** 仕分けは台帳で行う（`references/triage-ledger.md`）。
     - **依存メジャーバンプのAPIを検証するには、アプリの `vendor/autoload.php` を `bootstrapFiles` に加える**（または vendor を `scanDirectories`）。これが無いとバンプ後ライブラリのクラス/メソッドが `class.notFound` 扱いになり、**当のAPI破壊を検証できない**（依存バンプ検証はPHPStanの主目的の一つ）。
     - フレームワーク/プラグイン由来の関数（WordPressのACF `get_field()`/`update_field()` 等）は対応する stub パッケージ（`php-stubs/*`）を `scanFiles` で読ませ、`function.notFound` の大量誤検知を消してから本題の指摘を読む。誤ったPHPDoc（`@return int` なのに配列を返す等）由来の誤検知は、PHPDocを実体に合わせて解消する。
2. **ゲートを採用する前に、プローブで能動的に検証する。** 「0件しか出ないなら設定漏れを疑う」では足りない —— 疑うかどうかが人の裁量に委ねられ、実際には疑われない。`scripts/verify-gate.sh` を各ゲートに対して実行し、**VERIFIED / DEGRADED / BLIND の3値**を成果物に記録する。**「0 件」は、そのゲートが VERIFIED でない限り合格として扱ってはならない。** DEGRADED / BLIND のときは**穴埋めの担当ゲートを必ず明示する**（`references/detection-gates.md` §4）。
   - identifier ごとの下限 level は `scripts/probe-phpstan-levels.sh` で**プロジェクトごとに実測**する。スキル掲載の表（`references/detection-gates.md` §2）は参考値であり、運用閾値ではない。
3. 外部からロードされる定数・関数（本番専用設定ファイル等、gitignore対象でリポジトリに存在しないもの）がある場合、PHPStanの `bootstrapFiles` にスタブファイルを追加し、誤検知を防ぐ。詳細は `references/wordpress-notes.md`。

### フェーズ2: Rector 機械置換の実行（未適用の場合）

対象ブランチにまだ Rector を適用していない場合（dev ブランチ等をゼロから移行する場合）は、**他の手作業より先に、ここで Rector を実行する**。既に別ブランチで適用済み・マージ済みなら本フェーズはスキップしてフェーズ3へ進む。設定の詳細は `references/rector-config.md`。

1. **`rector.php` を用意する**（本番オートロード外・ルート配置）。
   - `withPaths()` は**コードベース全体**（対象バージョンで実行される全ソース）を指定する。フェーズ3のスコープ原則と同じく、名指しの少数ファイルに絞らない。
   - `withSkip()` に (a) 解析対象外パス（vendor・自動生成・ビルド成果物）、(b) 危険なルール（下記2）を指定する。除外パスは PHPStan/PHPCompatibility の除外設定と**完全一致**させる。
   - PHPバージョンセットは `withPhpSets(php83: true)` 等、または `LevelSetList::UP_TO_PHP_83`。
2. **危険なルールを `withSkip()` で除外する**。
   - **`ArrayToFirstClassCallableRector` は原則常に除外する**。`[$obj, 'method']` を第一級callable `$obj->method(...)` へ変換するが、これは (i) `--keep-compat` 時は下位バージョンでパースエラー、(ii) **完全移行でも**、WordPressのフックコールバック等「コールバックの同一性」に依存する箇所（`remove_action`/`remove_filter` での解除等）を壊す。**「完全移行だから安全」ではない**。
   - `--keep-compat` 指定時は加えて `never`/`readonly`/`enum`/コンストラクタプロパティ昇格 等のルールも除外する（`references/rector-config.md` の一覧）。
3. **まず `--dry-run` で実行し、適用予定を「ルール別」に確認する**。有用なルール（例: `NullToStrictStringFuncCallArgRector` によるnull弱点関数への `(string)` キャスト補完＝移行ガードそのもの）と、シグネチャを変える近代化ルール（`SetCookieRector`・`ReturnNeverTypeRector` 等）を区別する。想定外の広域変更が出たら `withSkip` を追加してから本適用する。
4. **本適用後、`git diff` を必ず人手でレビューする**。Rector の変更も「機械が正しいとは限らない」——シグネチャ変更・型追加・戻り値型付与は挙動やコールバック互換に影響しうる。レビュー後、論理単位でコミットする。
5. **Rector は出発点であって完了ではない**。機械置換で拾えない意味論的問題（未定義キー・null offset・`get_*_by()` false のプロパティ参照・静的コンテキストからの非static呼び出し等）は Rector では解消されない。それらはフェーズ3以降で潰す。

### フェーズ3: パターン別レビュー

**対象コード全体**（差分だけでなく、対象バージョンで実行されうる全クラス・全ファイル）を、以下のカテゴリで精査する。カテゴリ1（構文変換）とカテゴリ2（依存側API破壊）は `--keep-compat` の指定有無で主従が入れ替わる（並走運用＝カテゴリ1が主／完全移行＝カテゴリ2が主）。カテゴリ3以降は常時対象。各カテゴリの詳細・具体例は `references/breaking-changes.md` を参照。

> **スコープは「アプリ全体」を既定とする（最重要）**: レビュー対象を、事前にselectした少数ファイル（「影響が大きそうな ~10ファイル」等の名指しリスト）へ絞り込まないこと。`grep` や件数カウントを「すでに対象と決めたサブセット」にだけ回すと、**そのサブセット外の同型バグは件数にすら現れず、丸ごと見落とす**。静的解析ツール（フェーズ1）は最初から**コードベース全体**をスキャン対象に設定し、人手レビューも **allowlist（対象を数個選ぶ）ではなく denylist（全ファイルを候補に置き、除外するファイルは除外理由を記録する）** で進める。
>
> **除外理由の記録は成果物である。** 対象ファイル台帳（`references/triage-ledger.md` §5）に全ファイルを列挙し、除外したものには理由を書く。**ゲートは「`git ls-files` の全件 == 台帳の行数」。** 総数はこの行数一致で機械的に確定する。
>
> **静的解析が「0 件」でも、そのカテゴリの目視レビューを飛ばさない。** 件数はスコープの決定に使ってよいが、**スコープから外す根拠には使えない**。この誤りの実例（名指しリストから漏れたファイルの入れ子配列アクセスを、実データ実行まで検出できなかった件）は `references/detection-gates.md` §5 に全文を記録している。

1. **下位互換破壊構文**（**`--keep-compat` 指定時のみ**）: 機械置換ツールが `--to` 向けに「アップグレード」してしまった、`--keep-compat` バージョンではパースできない構文。第一級callable、`never`型、`readonly`プロパティ等。**`--keep-compat` 未指定（完全移行）ではこのカテゴリは対象外**——新構文はそのまま許容してよい。
2. **依存パッケージ側のAPI破壊的変更**（**`--keep-compat` 未指定＝完全移行では必須カテゴリ**。依存メジャーバンプを伴う場合も必須）: 依存パッケージのメジャーバンプで削除・リネームされたメソッド/関数（`gte()`→`greaterThanOrEquals()` 級）を、当該パッケージの CHANGELOG/UPGRADING と対象コードの呼び出し箇所で突合する。完全移行では構文互換（カテゴリ1）に代わってこれが本命。詳細は `references/breaking-changes.md` §6。
3. **未定義キー/プロパティ/変数への直接アクセス**: 配列・プロパティ・**変数**への直接アクセスがWarning/Deprecatedに格上げされていないか。REST/CSV等の外部入力を扱う箇所は特に優先度を上げる。
   - **未定義変数も PHP 8.0 で E_NOTICE → E_WARNING に格上げされている**（「7.xでも既にWarningだから対象外」は誤り）。7.x の既定 `error_reporting` は E_NOTICE を含まないため**移行するまで表面化しない**。最頻出は「条件分岐の中だけで代入され、分岐の外で無条件参照される変数」で、特にテンプレートを「引数あり/なし」の両方から読み込んでいる場合に片方の経路だけで壊れる。`variable.undefined` は最も低い感度から出るので全ファイルで潰しきる。詳細と実例は `references/breaking-changes.md` §2。
   - **「対象が無ければ `false`/`null` を返す関数」の戻り値を、ガードせず `->プロパティ` 参照している箇所**（`get_user_by()` / `get_post()` / `get_userdata()` 等）は、8.0 で「false に対するプロパティ読み取り」警告になる。**対象が存在しないデータでのみ顕在化する**ため実データ実行で出やすい。代入と参照の間にガードが無いものを機械的に洗い出す。**戻り値の型注釈が無い関数では最大感度でしか検出できない**（`references/detection-gates.md` §2）。
4. **暗黙型変換・null引数・キャストの副作用**: null を非null引数へ渡す（Fatal化）、`(string)`キャスト等でnull→空文字化した結果、その値をさらに`explode()`等へ渡した下流で新たな未定義キーアクセスが発生していないか（キャストで警告は消えても、下流のロジックまでは機械置換で保証されない）。
5. **非推奨/削除された関数・構文**: 対象バージョンで非推奨・削除された関数呼び出し。フレームワークのポリフィルで実質安全な場合は要件を確認の上、変換不要と判断してよい（判断根拠を記録する）。
6. **静的コンテキストからの非staticメソッド呼び出し（8.0でFatal化）**: staticメソッド内から `self::method()`（`method` が非static宣言）を呼ぶと、PHP 8.0 で `Error: Non-static method ... cannot be called statically` の**Fatal**になる（7.x は Deprecated で動作していた）。**`$this` を使っていなくてもFatal**。PHPStan の `method.staticCall` で機械検出できるので `level` を上げるまでもなく設定に含める。修正は、対象メソッドを `static` 化する（`$this` 不使用を確認したうえで）か、インスタンス経由呼び出しへ直す。WordPress等「クラスを名前空間代わりに `self::` 多用する」コードで発生しやすい。

**加えて、以下は機械検出が困難なため必ず目視で確認する**:

- **目視A: ネイティブクラスを継承した外部ライブラリのメソッド衝突**: `DateTime`/`DateTimeImmutable`/`ArrayObject`/`SplFileObject` 等のPHP内蔵クラスを継承する依存パッケージが、対象バージョンで新規追加されたネイティブメソッドと同名メソッドを（互換性のないシグネチャで）既に持っている場合、**継承整合性エラーとしてFatal Errorになる**。静的解析ツールはこのパターンを検出できないことが多い。依存パッケージのバージョンを上げずに対象バージョンへ引き上げる方針の場合は、`vendor/autoload.php` を対象バージョンの実行環境で読み込むだけの最小スクリプトを実行し、Fatal Errorが出ないか確認すること（詳細は `references/breaking-changes.md`）。
- **目視B: 外部通信ラッパーのエラーハンドリング**: HTTPクライアント等のラッパー関数が、通信失敗時の戻り値（例: WordPressの`wp_remote_get()`が返す`WP_Error`）を「空でない」という理由だけで正常系として扱っていないか。対象バージョンでの型チェック強化により、こうした既存の潜在バグが顕在化・Fatal化することがある。
- **目視C: 無警告で結果だけが変わるセマンティクス変更**（`references/breaking-changes.md` §7-a）: 非厳密比較（`==`・`in_array()`・`switch`・`array_search()`）、`htmlspecialchars()` の既定フラグ、文字列関数のロケール非依存化、`str_split('')`、PDO の型返し等。**どの静的解析でも検出できない。** `grep '=='` でも見つからない（`in_array()` に `==` は現れない）。移行元・移行先での**出力 diff** が唯一の検出手段である。棚卸しの手順は `references/triage-ledger.md` §3。
- **目視D: 移行作業が作り込む呼び出し規約の不整合**（同 §7-b）: 引数の形・意味を変えたのに、呼び出し側と受け側の片方しか直っていない類型。**移行前には存在しなかった欠陥**なので「移行で壊れたか」を静的解析で確かめても出てこない。引数の形を変えたら**全呼び出し箇所を grep で列挙してから**着手し、呼び出し側と受け側を**同一コミットで対にして**修正する。

### フェーズ4: 仕分けと修正

#### 4-A 仕分け（修正より先に、必ず独立した工程として行う）

検出した指摘を、**1件ずつ**「実対応要」「偽陽性」「保留」へ判定し、**根拠つきで台帳へ記録する**。書式は `references/triage-ledger.md`、空の雛形は `references/triage-ledger-template.md`。

| 規定 | 内容 |
|---|---|
| **ゲートは「未仕分け 0 件」** | 「指摘 0 件」ではない。件数は欠陥数ではなく、件数を合格条件にすると抑止するインセンティブが生まれる |
| **根拠の無い偽陽性判定を認めない** | 判定根拠は「到達不能であることを示す」か「実測で示す」のいずれか。空欄・実質空欄は未仕分け扱い（機械検査する） |
| **判定不能は「未判定」のまま残す** | 偽陽性へ倒さない。ゲートは FAIL のままにし、判定不能であること自体を成果物に書いてエスカレーションする |
| **消えた指摘を台帳から削除しない** | `resolved: <日付>` と理由を1行書いて残す。黙って消すと、再発したときに「初めて出た」と誤認する |
| **外部入力を起点とする箇所は記録する** | 認可・型・範囲の検査が無ければ「移行スコープ外の別課題」として記録しエスカレーションする。**移行のついでに直さない**（挙動変更になる）。**記録せずに素通りさせない** |

`scripts/phpstan-gate.sh --triage=<台帳>` が「観測 − 台帳 = 未仕分け」を機械判定する。

#### 4-B 修正

検出した項目を、論理的に等価な修正で解消する。

- **`--keep-compat` 違反**: 下位互換な書き方へ機械的・網羅的に置換する。置換方式は「Rector再実行」と「正規表現等によるピンポイント置換」の2択があるが、後者を推奨する（Rector再実行は無関係な差分も動かしてしまい、既にレビュー済みの差分の再検証が必要になるため）。置換漏れ・置換ミスの両方は、フェーズ1の静的解析ゲート（ERROR 0件）の再実行で機械検出する。
- **未定義キー/型不整合**: `?? デフォルト値` やガード節（`if (!isset(...)) { return; }` 等）で明示的に処理する。警告を握りつぶす（`@`演算子等）のではなく、意図を明示したうえで安全側に倒す。
  - **フォールバック値は「捏造」しない**: 取得できないデータ（`get_user_by()` が `false` を返す、外部lookupの失敗等）に対し、警告を消す目的で**現在時刻・`0`・ダミー文字列などの意味のない既定値をでっち上げてはならない**。捏造した値は「正しく見えるが誤ったデータ」（誤った日付・金額・ID等）を下流へ流し込み、E_WARNING より悪い障害（誤ったデータに基づく処理の実行）を生みうる。データが本当に存在しないなら、フォールバックを作らず **`null`／空文字を返す**のが正直で安全。「警告を消す」ことと「正しく振る舞う」ことを混同しない。
  - **`null`/空を返す前に、呼び出し元がそれを許容するか確認する**: 早期 `return null;` する場合、呼び出し元が空/`null` を扱えるか（`strlen((string)$x)` / `empty()` / `?:` 等で分岐しているか）を必ず確認してから返す。許容していない呼び出し元があるなら、その側にもガードを追加する。実例: あるメソッドで無効ユーザー時に「現在時刻フォールバック」を入れかけたが、呼び出し元が既に空を許容していたため `return null;` に改めた。
  - **権限・種別・フラグの `??` 既定値は、必ず最も権限の低い値／不許可側にする。** 「捏造しない」規定はデータ値だけでなく権限にも適用する。
  - **比較演算子を緩める方向の修正を禁止する。** `===` は `===` のまま、型を合わせるのは値の生成側で行う。型不一致の解消目的でキャストを挟んで型ジャグリング比較へ後退させない。
  - **ガードを入れて認可分岐を飛ばさない。** 指摘は「値が無いかもしれない」であって「無いときどうすべきか」は教えない。判定に関与する箇所は安全側（拒否・中断）に倒す。
- **同一ソースの全キーを同時に処理する**: ある取得結果の1キーだけを直して他を残さない。同じ取得結果から読むキーは**まとめてガードする**。
- **修正後は再発防止策を検討する**: 機械置換ツールの設定に、今回問題になったルールのskip設定を追加する等。
- **修正のたびに静的解析ゲートを再実行し、新規の指摘が出ていないことを確認する。** **件数の増減で判定しない。行単位の差分で判定する** —— 件数が同じでも中身が入れ替わっていることがある（ガードを足して1件減り、別の identifier が1件増える等）。`--format=tsv` の出力を `diff -u` にかけ、`+` 行が1本でもあれば新規指摘とみなす（`references/detection-gates.md` §7）。

### フェーズ5: 動作確認

1. 静的ゲートを最終確認する。**合格条件は「未仕分け 0 件」であり、「指摘 0 件」ではない。** 各ゲートについて自己検証の結果（VERIFIED / DEGRADED / BLIND）を併記する（`references/detection-gates.md` §6）。
2. 対象バージョンの実行環境（可能であればDockerやDDEV等でバージョンを固定した環境）で、主要フローをE2Eで確認する。ログ監視（`Deprecated`/`Warning`/`Fatal`をgrep）を並行する。
   - **バッチ/cron/CSV/インポート等の一括処理は、実データで必ず実行する（静的解析では出ない層）**: `$data[$key]['x']`（外側キーが特定のレコードでだけ欠ける）のような「特定のデータ形状でだけ null/未定義キーになる」警告は、PHPStanの感度を上げても、またクリーンな少数データのスモークテストでも出ないことがある。**実データ（本番相当の多様なレコード）を流して初めて表面化する**ため、対象バージョンのバイナリで cron/バッチを実行し、警告を収集して潰す。特に出力バッファへ警告が混入するCSV/JSON生成経路は、混入＝ファイル破損に直結するため優先。
   - **収集の手段を用意する**: `scripts/php-migration-logger.php`（WordPress は `scripts/wordpress/00-php-migration-logger.php`）を設置し、`scripts/aggregate-migration-log.sh` で集計する。設置・撤去・ログに書かない情報の規定は `references/runtime-detection.md`。**設置しない選択肢を先に検討する**（標準のエラーログで足りることが多い）。
   - **実データ実行は最大のリスクでもある**: メール送信・決済 API 呼び出し・外部連携が**実際に走る**。(1) ステージング＋本番データのコピーを既定とし、(2) 本番で避けられない場合は**外部送信をブロックする手段を先に確認し**、(3) 冪等でない処理は実行しない。本番ホストで実行してよいコマンドの allowlist は `references/runtime-detection.md` §5。**「実データで流せ」だけを指示して送信抑止に触れないのは危険である。**
   - **実行時に出て静的解析が沈黙した箇所は、ツールの限界と結論づける前に設定を疑う**: (1) 下限 level、(2) 守備範囲、(3) stub / bootstrapFiles、(4) `ignoreErrors` / baseline の4点を確認する。突合は `scripts/correlate-static-runtime.sh`（`--rev` 必須）。**区分Bが0件でも「0件だった」と記録する。**
3. 実行環境が用意できない場合は、静的検証の結果を持って「機械的に検出可能な問題はゼロである」ことを成果とし、**動的検証（実環境E2E）は別途手動で実施する項目として明示的にチェックリスト化**して引き継ぐ。静的検証だけで「動作確認完了」と報告しない。
4. ローカルの検証用PHPコマンドが対象バージョンと異なる場合（例: ローカルCLIが8.4で対象が8.3）、ローカル実行で出た警告がローカル特有のものか対象バージョン特有のものかを区別する。静的解析の `phpVersion`/`testVersion` 設定を対象バージョンに固定していれば、そちらを信頼する。
5. **移行先環境のエラー表示設定は、推測せず必ず実測する**。「フレームワークが本番では出さないようにしているはず」は成り立たない（WordPress の場合、`WP_DEBUG=false` は `display_errors` を一切変更せず、かつ `error_reporting` に E_WARNING を含む）。確認は「php.ini の値」ではなく**実際のリクエストが見る値**で行う（php-fpm のプール設定・`.htaccess`・`.user.ini`・フレームワークの `ini_set` が重なるため、CLI の `php -i` は答えにならない）。チェック項目 S1〜S9 と是正手順は `references/runtime-detection.md` §4。**移行前・移行後の両方で取得し、差分を成果物に残す**（記録が無いと、見つけた設定が「元からそうだった」のか「移行で変わった」のか判別できない）。
6. **テスト/ステージング環境から報告されたエラーは、まず「その環境がどのコミットを動かしているか」を確認してから解釈する**。報告された症状は次の3通りがありうる:
   1. 未知の新規バグ
   2. **別ブランチでは修正済みだが、この環境が動かしているブランチには未適用**
   3. 修正済みだが、その環境へまだデプロイされていない
   確認せずに 2/3 を 1 と誤認すると、原因調査を空振りさせる。逆に「修正済みのはず」と決めつけると、実際には未適用の修正を見逃す。**該当ファイルの当該行を、対象ブランチの `git show <branch>:<path>` で直接確認する**のが最短。
7. **報告された1件だけを直して終わりにしない**。エラーは同型の欠陥が複数あるうちの、たまたま先に踏まれた1件であることが多い。報告を受けたら、その欠陥のカテゴリで**全ファイルを機械的に再走査**し（例: 未定義変数なら PHPStan の `variable.undefined` を全件抽出）、同型を一括で潰す。実例: テスト環境で報告された未定義変数は1件だったが、同一ブランチに同型が8件残っていた。**この対象には「他者が手で直したコミット」も含める** —— 誰かが個別に直した箇所は、同型が他にも残っている強い手がかりである。

### フェーズ6: 移行後フィードバック

移行完了後、**ゲートの取りこぼしをスキルへ還流させる**。実施しないと、同じ検出漏れが次の移行でそのまま再現する。

1. 対象は3種: (a) 実行時ログに出た欠陥、(b) 本番・ステージングからの障害報告、(c) **他者が手で直したコミット**。**それぞれについて、0 件でも「0 件だった」行を残す**（行が1つも無い台帳は「未実施」と区別できない）。
2. 各件について「どのゲートなら検出できたか（`detectable_by`）」と「**なぜ取りこぼしたか（`why_missed`）**」を、W1〜W8 の分類コードから選んで記録する（`references/triage-ledger.md` §6）。
3. **`why_missed` が W1〜W6（＝スキルの欠陥）なら、`skill_action` に「対応不要」と書いてはならない。** W7（ツールの原理的限界）へ逃げていないかを必ず確認する。また `verified_by` が「未検証」の行は結論として使えない（「検出できたはず」を検証せずに書かない）。
4. **同じ `why_missed` コードが前回の突合にも存在したら再発である。** 前回の修正が効いていないので、修正内容そのものを見直す。

## 出力

作業完了時、以下3点を成果物として整理する。

1. **修正済みブランチ**（コミットは論理単位で分割し、各コミットメッセージに検出内容と修正方針を記録する）。**変更ファイルの一覧として `git diff --name-only <base>..<head>` の出力をそのまま貼る**（要約や抜粋にしない。抜けたファイルは無かったことになる）。
2. **ゲート結果の報告ブロック**（`references/detection-gates.md` §6 の書式）。**level と、有効／除外 identifier を必ず併記する。** 除外した identifier には理由を書く。自己検証していないゲートの「0 件」を `PASS` と書かない。
3. **カテゴリ別検出・修正一覧**（フェーズ3の各カテゴリ＋目視確認A〜Dごとに、件数・主な修正内容・「確認のみで修正不要と判断した」項目とその根拠を記録する）
4. **仕分け台帳**（`references/triage-ledger.md` の各種。未仕分け 0 件であることを示す）
5. **残存懸念と手動確認項目**（フェーズ5で実施できなかった動的検証をチェックリスト化したもの。外部連携等のクリティカルなフローがある場合は優先度を明記する）

- `references/wordpress-notes.md`: WordPress固有の注意点（ACF戻り値契約・偽陽性パターン集・`wp_debug_mode()` の実挙動）
- `scripts/lint-target-version.sh`: 指定PHPバージョンでの一括構文チェック
- `scripts/probe-phpstan-levels.sh`: identifier ごとの下限 level を**プロジェクトで実測**する
- `scripts/phpstan-gate.sh`: 「未仕分け 0 件」でゲート判定する（台帳との差集合）
- `scripts/verify-gate.sh`: ゲートが実際に検出できるかを能動検証する（VERIFIED / DEGRADED / BLIND）
- `scripts/php-migration-logger.php` / `scripts/wordpress/00-php-migration-logger.php`: 実行時エラーロガー
- `scripts/aggregate-migration-log.sh`: 実行時ログの集計（BOOT 記録が無ければ判定不能）
- `scripts/correlate-static-runtime.sh`: 実行時ログと静的解析の突合（`--rev` 必須）
- `scripts/php8-identifiers.txt`: identifier ホワイトリストの既定値
- `scripts/lib/find-bin.sh`: バイナリ探索の共有関数（`source` して使う）
