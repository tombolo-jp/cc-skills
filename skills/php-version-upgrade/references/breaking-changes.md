# PHP破壊的変更カタログ

**本カタログは「何を探すか」を定義する。検出方法の設定値（level・ゲートの守備範囲）は `references/detection-gates.md` を正とし、本ファイルには数値を書かない。**

汎用的に使えるよう、バージョン非依存のパターン分類と、7.4→8.3移行で実際に遭遇した具体例を併記する。新しいバージョン範囲を扱う場合は、該当PHPバージョンのUPGRADING/移行ガイドで同種のパターンを追加調査すること。

**この表に載っていれば全部見つかる、ではない。** §7 は**どの静的解析でも検出できない類型**を集めている。早見表の P9・P10 がそれにあたる。

## 1. 構文レベルの破壊的変更（`--keep-compat` 対象）

機械置換ツール（Rector等）の「バージョン上限指定」ルールセットが、意図せず対象バージョン専用構文へアップグレードしてしまう代表例。**旧バージョンでパースエラー（Fatal）になる**ため、並走期間がある移行では最優先で潰す。

| 構文 | 導入バージョン | 典型的な誤爆パターン |
|---|---|---|
| 第一級callable `$this->method(...)` | PHP 8.1 | `[$this, 'method']` からの「アップグレード」 |
| `never` 戻り値型 | PHP 8.1 | 常に例外/exitで終わるメソッドへの型注釈追加 |
| `readonly` プロパティ | PHP 8.1 | コンストラクタで一度だけ代入されるプロパティへの注釈追加 |
| enum | PHP 8.1 | 定数配列からの変換 |
| コンストラクタプロパティ昇格 | PHP 8.0 | 冗長な `private $x; __construct($x) { $this->x = $x; }` からの圧縮 |
| named arguments | PHP 8.0 | 呼び出し側の引数明示化（構文自体は8.0未満で無視されずパースエラー） |
| `match` 式 | PHP 8.0 | `switch` からの変換 |
| union型宣言 `int\|string` | PHP 8.0 | 型注釈の拡張 |

**注意**: `#[Attribute]` 構文（PHP 8.0+）は例外的に、8.0未満でも `#` が単一行コメントとして解釈されるため**パースエラーにならない**（後方互換性を考慮した設計）。7.4混在コードでライブラリ側が `#[ReturnTypeWillChange]` 等を使っていても、それ自体は問題にならない。

**対処**: 該当ルール（例: Rectorなら `Rector\Php81\Rector\Array_\ArrayToFirstClassCallableRector`、`Rector\TypeDeclaration\Rector\ClassMethod\ReturnNeverTypeRector`）を機械置換ツールの設定から `withSkip()` 等で除外し、再発を防止する。

## 2. 未定義キー/プロパティ/**変数**アクセスの重大度格上げ

PHP 8.0 の「Reclassifying engine warnings」RFC による格上げ。

| 変更 | バージョン | 7.4以前 | 8.x |
|---|---|---|---|
| 未定義配列キー | PHP 8.0 | E_NOTICE | **E_WARNING** |
| 未定義プロパティ | PHP 8.0〜8.2 | E_NOTICE | E_WARNING → 8.2でDeprecated |
| **未定義変数** | **PHP 8.0** | **E_NOTICE** | **E_WARNING** |

**未定義変数も対象である**（7.x で既に Warning、という認識は誤り）。実測（PHP 7.4.30 / 8.3.30、`error_reporting(E_ALL)`）:

```
7.4 : Notice:  Undefined variable: is_target_type
8.3 : Warning: Undefined variable $is_target_type
```

### なぜ移行するまで気づかないのか（重要）

**7.x の既定 `error_reporting` は E_NOTICE を含まない**（php.ini 無指定時の実測値 `22519` = `E_ALL & ~E_NOTICE & ~E_STRICT & ~E_DEPRECATED`）。したがって未定義変数/キーは**7.x では「エラーが出ていなかった」のではなく「出ていたが既定設定で抑制されていた」**。8.0 で E_WARNING へ格上げされると既定設定に含まれるようになり、**同じコードが突然警告を出し始める**。

このため、レビュー時は次を必ず確認する:

- **移行先環境の `error_reporting` / `display_errors` を実際に確認する。** 同じコードでもサーバ設定次第で「無風」にも「警告だらけ」にもなる。テスト環境で `display_errors=On` なら画面に露出し、本番で `Off` なら見えないままログを汚し続ける。どちらも放置しない。
- 静的解析側は `error_reporting` に依存しない。**PHPStan の `variable.undefined` は最も低い感度から出る**ので、感度を上げるまでもなく全ファイルを走査して潰しきる（下限は `references/detection-gates.md` §2）。

### 最頻出パターン: 条件分岐の中だけで代入され、分岐の外で無条件参照される変数

```php
if (!empty($user)) {
    $type = get_field('item_type', $post_id);
    $is_target_type = ($type == 'special');   // ← ここでしか代入されない
}
// ...
if ($is_target_type) { ... }   // ← $user が空の経路では未定義（8.0 で E_WARNING）
```

**対処**: 分岐の手前で初期化する（`$is_target_type = false;`）。`??` で読み出し側を都度ガードするより、宣言位置が明示されて安全。

**特に危険なのがテンプレート/ビュー層**。同じテンプレートが「引数あり」と「引数なし」の両方から読み込まれると、片方の経路でだけ未定義になる。WordPress の例:

```php
get_template_part('parts/detail-table', null, $current_user); // $args あり
get_template_part('parts/detail-table');                      // $args なし ← こちらで壊れる
```

**同一テンプレートの全呼び出し箇所を列挙してから**判断すること（`grep "get_template_part('parts/<name>'"`）。実例として、あるプロジェクトでは引数ありで読み込むページでは正常だったのに、引数なしで読み込む別のページでのみ毎回3件の警告が出ていた。

> **補足（WordPress）**: テンプレート内の `$args` 自体は未定義にならない。WPコアの `load_template($_template_file, $load_once, $args = array())` が `$args` を仮引数として持つため、インクルード先スコープでは常に定義済み。PHPStan はこれを解釈できず `variable.undefined` を出すので、**この1件だけは根拠を明記して baseline 化してよい**（他の未定義変数は実バグとして必ず修正する）。

REST API・CSV/Excelインポート等、**外部入力を扱う配列アクセス**（`$_REQUEST[...]`、`$request->get_params()`の結果等）は優先的にレビューする。レスポンス/出力に警告文字列が混入すると、JSON破壊やCSV破損につながる。

## 3. 暗黙型変換・null引数

| 変更 | バージョン | 内容 |
|---|---|---|
| null を非nullable内部関数引数へ渡す | PHP 8.1 | Deprecated（将来的にTypeError化予定） |
| 暗黙のfloat→int精度落ち | PHP 8.1 | Deprecated |
| 数値文字列の比較 | PHP 8.0 | 非数値文字列との比較挙動が変更（`0 == "abc"` が false に） |

**キャストの副作用に注意**: `(string) $value` でnullを空文字化すると警告は消えるが、その値を `explode()` に渡すと `['']`（1要素配列）になる。後続コードが `$result[1]`, `$result[3]` 等の固定インデックスへ無条件アクセスしていると、そちらで新たな未定義キー警告が発生する。**機械置換はキャスト追加までは行うが、下流のインデックスアクセスの安全性までは保証しない**。人手レビューが必須。

## 4. 非推奨/削除された関数

対象バージョンで削除された関数を使っていないか確認する。フレームワーク側でポリフィルが提供されている場合（例: WordPress 5.9+の `wp-includes/compat.php` が `str_contains`/`str_starts_with`/`str_ends_with` 等をポリフィル）、無理に書き換える必要はない。ただしポリフィル提供バージョンと実際の稼働バージョンの整合は確認すること。

## 5. ネイティブクラスを継承した依存パッケージのメソッド衝突（機械検出困難）

**【`--keep-compat` 指定＝依存据え置き時の最終手段】** 本節のパッチ対処は、並走運用などで依存パッケージをメジャーバンプできず据え置く場合の逃げ道である。`--keep-compat` 未指定の**完全移行では依存メジャーバンプが標準工程**（SKILL.md フェーズ0）であり、衝突は依存を対象バージョン対応版へ上げれば解消することが多い。したがって完全移行では下記「対処の選択肢」の1（依存更新）を最優先し、パッチ（選択肢2）はバージョン制約が両立しない例外時に限る。あわせて依存を上げる以上、§6（依存側API破壊）の突合が本命になる。

**発見の経緯**: `DateTimeImmutable` を継承するサードパーティの日時ライブラリが、PHP 8.3で新規追加された `DateTimeImmutable::createFromTimestamp(int|float $timestamp): static` と同名メソッドを、より狭い型宣言（`createFromTimestamp(int $timestamp): <ライブラリ独自の日時インタフェース>`）で既に持っていた。PHPの継承整合性チェックにより、**クラス宣言の読み込み時点で catchできない Fatal Error** になる。

このパターンの危険な点:

- **静的解析ツールで検出できないことが多い**（PHPStan/PHPCompatibilityは主にアプリケーションコードを対象とし、vendor配下の継承関係の互換性までは通常チェックしない）。
- 該当クラスが **composerの `files` autoload**（`vendor/autoload.php` 読み込み時に無条件実行されるファイル）で参照されている場合、**アプリケーションの機能を一切使わなくても、リクエストのたびに確実にFatalする**。影響範囲の当たりが外れやすい。
- 依存パッケージのバージョンを上げれば直ることが多いが、上げると別のバージョン要求（例: 「シグネチャ修正版は逆に対象バージョンより新しいPHPを要求する」）と衝突し、**移行元/移行先どちらの単純なバージョン指定でも両立しない**ことがある。

**検出方法**:

1. 依存パッケージが `extends DateTime`/`DateTimeImmutable`/`DateInterval`/`ArrayObject`/`SplFileObject` 等、PHP内蔵クラスを継承していないか `grep -rn "^class .* extends " vendor/` で確認する。
2. 該当パッケージの全公開クラスについて、対象バージョンの実行環境で `php -r "require 'vendor/autoload.php'; class_exists('Vendor\\ClassName');"` を個別実行し、Fatal Errorが出ないか確認する。`vendor/autoload.php` の読み込みだけでFatalする場合は `composer/autoload_files.php` に無条件実行ファイルが含まれていないか確認する。
3. 対象バージョンで新規追加された `DateTime`系のメソッド一覧は `php -r "print_r((new ReflectionClass('DateTimeImmutable'))->getMethods());"` を対象バージョンの実行環境で実行して取得し、依存パッケージ側のメソッド一覧と突き合わせる。

**対処の選択肢**（優先順）:

1. 依存パッケージを、移行元・移行先どちらの制約も満たすバージョンへ更新する（存在すれば最も安全）。
2. 存在しない場合、`cweagans/composer-patches`（または同等の仕組み）で**該当メソッドの型宣言だけを最小限に緩和するパッチ**を作成し、composerのインストール/更新のたびに自動再適用させる。vendorディレクトリを直接手編集して終わりにしない（`composer update` で静かに消え、再発に気づけない）。パッチには変更理由・元の型・緩和後の型・将来パッチを外せる条件（依存メジャーバンプ等）を明記する。
   - 型宣言を緩和する際、`--keep-compat` の制約（本カタログ §1）を必ず守ること。例えば `int|float` のようなunion型宣言は8.0+構文のため、7.4互換を維持する場合は型宣言そのものを除去する（無型は最も緩い型としてどのバージョンでも安全）。
3. 依存パッケージの使用箇所をネイティブクラスへの直接依存に置き換える（影響範囲・回帰リスクが大きいため最終手段）。

## 6. 依存パッケージのメジャーバンプに伴うAPI破壊的変更（PHPバージョン対応そのものとは別軸）

**【`--keep-compat` 未指定＝完全移行時の主戦場】** 完全移行では依存メジャーバンプが標準工程となるため（SKILL.md フェーズ0・フェーズ3カテゴリ2）、構文互換（§1）に代わって本節が本命リスクになる。`gte()`→`greaterThanOrEquals()` 級の「削除・リネームされたメソッド」を CHANGELOG/UPGRADING と対象コードで突合する作業を、完全移行では必須カテゴリとして扱うこと。据え置き（`--keep-compat` 指定で依存をバンプしない）場合はこの主戦場は発生せず、代わりに §5 のパッチ対処が焦点になる。

**発見の経緯**: あるブランチで「PHPバージョン対応と同時に依存パッケージもメジャーバンプする」方針を採った結果、日時ライブラリの `gte()`（`greaterThanOrEquals()` の短縮エイリアス）メソッドが新メジャーバージョンで削除されており、`Call to undefined method` の実行時エラー（Fatal）を起こしていた。PHPStanの静的解析で機械検出できた（未定義メソッド呼び出しとして通常のlevel設定で検出可能）が、**PHPバージョン対応の作業だからといってPHPの構文・組み込み関数だけをレビューし、依存パッケージ自体のAPI変更を見落とすと、この種の回帰は静的解析を導入していても「対象外」として見過ごされやすい**（PHPCompatibilityはPHP本体の互換性のみを見る、依存パッケージのバージョン間差分は見ない）。

**教訓**: 依存パッケージのメジャーバージョンを同時に上げる場合は、PHPバージョン対応のレビューとは別に、**依存パッケージ自体のCHANGELOG/UPGRADING文書を確認し、リネーム・削除されたメソッド/関数がないかを確認する**。フェーズ1で導入するPHPStanは対象コードのpaths配下しか解析しないことが多いため、依存パッケージ側のAPI変更由来のエラーも実際に拾えるかを確認する（`excludePaths`でvendorを除外していても、**呼び出し側のアプリケーションコードで「存在しないメソッドを呼んでいる」ことは検出できる**——ただし依存パッケージの実体（vendor配下）がその対象バージョンで実際にインストールされていることが前提）。

このため、依存メジャーバンプを伴う移行では、フェーズ3のレビュー観点に以下を追加する:

- 依存パッケージのメジャーバージョン間で削除・リネームされたメソッド/関数の一覧を、当該パッケージのUPGRADING/CHANGELOGから収集する。
- 収集した一覧と、対象コードでの当該メソッド呼び出し箇所を突き合わせる（`grep -rn -- "->旧メソッド名("` 等）。
- 突き合わせは**必ず対象バージョンの依存パッケージを実際にインストール（`composer install`）した状態で**行う。ロックファイル上のバージョン表記だけでなく、実際に配置されたコードを見て確認する。

| P10 | **移行作業が作り込む呼び出し規約の不整合**（本カタログ §7-b） | **どのツールも無力。** 全呼び出し箇所の grep 列挙と、呼び出し側・受け側の対での修正 | **最高**（移行前には存在しなかった欠陥を、移行作業自体が作る） |

## 7. エラーを出さない類型（★静的解析で検出できない）

**本節の類型は警告を一切出さない。** §1〜§6 は「警告・Fatal として現れるもの」を扱うが、ここに集めたものは**結果だけが静かに変わる**。早見表の P9・P10 がこれにあたる。

### 7-a PHP のセマンティクス変更に起因するもの

| # | 変更 | 導入 | 無警告で起きること | 静的解析で拾える条件 | 検出手段 | 波及する構文 |
|---|---|---|---|---|---|---|
| N1 | 文字列⇔数値の非厳密比較 | 8.0 | `0 == "abc"` が true→false。**条件分岐が丸ごと反転する** | 両辺の型が静的に確定する場合のみ `equal.alwaysFalse` 等。DB・外部入力由来の `mixed` では**不能** | 移行元と移行先で同一処理の出力を diff する | `in_array()` / `array_search()` / `switch` / 2引数 `array_keys()` / `==` / `!=` |
| N2 | `false` が絡む非厳密比較 | （変更なし。**注意点として掲載**） | `false == ""` / `false == "0"` / `false == []` はいずれも**7.4 でも 8.3 でも true**。取得失敗の `false` が空文字・空配列と等値になる | 同上 | 同上 | `get_user_by()` / `get_post()` / ACF の取得系など「無ければ false」を返す関数の戻り値判定 |
| N3 | `htmlspecialchars()` の既定フラグ | 8.1 | 既定が `ENT_QUOTES \| ENT_SUBSTITUTE \| ENT_HTML401` へ変更。**シングルクォートが変換されるようになる** | 不能 | 出力 diff（特に属性値・JSON 埋め込み） | `htmlspecialchars()` / `htmlentities()` / `html_entity_decode()` |
| N4 | 文字列関数のロケール非依存化 | 8.2 | `strtolower()` 等が ASCII のみを対象にする。**ロケール依存だった変換結果が変わる** | 不能 | 出力 diff | `strtolower()` / `strtoupper()` / `ucfirst()` / `ucwords()` |
| N5 | `ksort()` 等の比較方式 | 8.2 | 数値文字列キーの並び順が変わりうる | 不能 | 出力 diff（一覧の並び順） | `ksort()` / `krsort()` / `asort()` / `sort()` |
| N6 | `str_split('')` の戻り値 | 8.2 | `['']`（1要素）→ `[]`（空配列）。**`count()` が 1 から 0 になる** | 不能 | 出力 diff | `str_split()` の直後の `count()` / `foreach` |
| N7 | PDO が int/float をネイティブ型で返す | 8.1 | 数値カラムが文字列ではなく int/float で返る。**`===` 比較や `is_string()` 判定が反転する** | 不能 | 出力 diff（DB 由来の値を厳密比較している箇所） | `PDO::fetch()` の結果に対する `===` / `is_string()` / `in_array(..., true)` |

**N1 の実測（PHP 7.4.30 / 8.3.23 の両実機）** —— `in_array()` を `grep '=='` で探しても見つからない、という一点がこの表の存在理由である。

```
★変化  in_array("abc", [0])   7.4=true -> 8.3=false      不変  in_array("1", [1])    true
★変化  in_array("", [0])      7.4=true -> 8.3=false      不変  in_array("03", [3])   true
★変化  in_array(0, ["abc"])   7.4=true -> 8.3=false      不変  in_array(" 1", [1])   true
★変化  in_array(0, [""])      7.4=true -> 8.3=false      不変  in_array(null, [""])  true
★変化  in_array("1abc", [1])  7.4=true -> 8.3=false      不変  in_array(false, [""]) true
```

**判定則** —— 結果が変わりうるのは次の2条件のいずれかを満たす場合**のみ**である。PHP 8.0 で変わったのは比較全般ではなく **int|float ⇔ string** の1組合せだけである。

- **(A)** needle が `int|float` になりうる **かつ** haystack に**非数値文字列**（`""` を含む）の要素がありうる
- **(B)** needle が**非数値文字列**（`""` を含む）になりうる **かつ** haystack に `int|float` の要素がありうる

安全（両バージョンで結果が同一）: string⇔string ／ int⇔int・float ／ int⇔**数値**文字列 ／ bool⇔任意 ／ null⇔任意 ／ array⇔非array。

この判定則により、needle と haystack の「int/float が入りうるか」「非数値文字列が入りうるか」の**2ビットだけで機械的に切り分けられる**。「数値⇔文字列で混ざるか」という粗い基準より判定コストが1桁下がる。棚卸しの手順と台帳の書式は `references/triage-ledger.md` §3 に従う。

**厳密比較化するときの注意**: 第3引数 `true` を付けるだけで壊れる組み合わせがある。例えば `wp_date('j')`（**数値文字列**）⇔ `range(3, 19)`（**int[]**）は、7.4 でも 8.3 でも結果は同じだが、`true` を付けると即座に false になる。**needle 側のキャストを同時に入れること**（`in_array((int) wp_date('j'), range(3, 19), true)`）。

### 7-b 移行作業自体が作り込む呼び出し規約の不整合

> **本節は PHP の破壊的変更ではない。** 無警告で壊れる類型を一箇所で読めるようにするため、便宜上このカタログに置いている。

**実例**: 移行のリファクタリングで、あるテンプレートへ渡す引数の形を「文字列」から「配列」へ変えた。呼び出し側2箇所（`page-signup.php:82,95`）は配列を渡すよう修正されたが、受け側（`payment-fields-tr1.php:13,15,24,26`）は `$args == 'credit'` のままだった。結果、**注記4種が一切描画されなくなった**。エラーは1件も出ていない。

**なぜどのツールも無力か**

- **PHPCompatibility**: PHP 本体の互換性しか見ない。呼び出し規約はアプリ固有であり守備範囲外である。
- **PHPStan**: 受け側の変数は「呼び出し元から渡される値」であり、フレームワークのテンプレート機構を介すと型が追跡できない。`mixed == 'credit'` は型として正当である。
- **実行時ログ**: 警告が出ない。`配列 == 文字列` は false を返すだけで、エラーではない。
- **テスト**: 「描画されるべきものが描画されない」ことを検査していない限り通過する。

**規定**

| # | 規定 |
|---|---|
| 1 | 呼び出し側と受け側は**同一コミットで対にして修正する**。片側だけのコミットを作らない |
| 2 | 引数の形・意味を変えたら、**全呼び出し箇所を grep で列挙してから**修正に着手する。「主要な呼び出し元」を先に決めない |
| 3 | 列挙した全箇所を1件ずつ消し込む。消し込みの成果物は `references/triage-ledger.md` §5（対象ファイル台帳）と同じ形式で残す |
| 4 | 「描画されるはずのもの」「返るはずの値」を、**移行前後の出力 diff** で確認する（N1〜N7 と同じ手段） |

**この類型は移行前には存在しなかった欠陥である。** 「移行で壊れたか」を静的解析で確かめても出てこない。**移行作業のレビューで対にして見る以外に方法がない。**
