# 検出ゲート — どう探せば見つかるか

**本ファイルは「どう探せば見つかるか」を定義する。各 identifier がどのパターンに対応するかは `references/breaking-changes.md` を参照する。**

**level・バージョン・件数などの数値は、スキル全体でこのファイルだけに書く。** 他のファイルは identifier 名とこのファイルへの参照で記述する。数値が2箇所にあると必ず片方が古くなり、根拠のない数値が生き残る。

すべてのゲートは3つの属性で記述する。**追加・変更するときはこの3つを必ず埋める。**

| 属性 | 意味 | 埋めないと起きること |
|---|---|---|
| 守備範囲 | そのゲートが**原理的に何を見るか** | 見ないものを見ていると思い込む |
| 感度 | 設定（level 等）によって**どこから検出されるか** | 弱い設定のまま「0件＝合格」と読む |
| 前提 | stub・bootstrap・対象パスなど、**成立に必要な条件** | 前提が欠けたまま 0 件になる |

---

## §1 ゲート一覧と守備範囲

| ゲート | 守備範囲（見るもの） | 原理的に見ないもの |
|---|---|---|
| PHPCompatibility（phpcs） | 削除・非推奨になった関数/定数/構文の**呼び出しの有無** | 値の型・実行経路・データ依存の挙動 |
| PHPStan | 型推論に基づく**意味論的な誤り**（未定義キー/プロパティ/変数、null 引数、非 static 呼び出し等） | 実データでのみ現れる形状、比較セマンティクスの変化（両辺が mixed のとき）、呼び出し規約の片側変更 |
| 対象バージョンの `php -l` | **構文**が対象バージョンでパースできるか | 実行しないと分からないもの全般 |
| 実行時ログ（`scripts/php-migration-logger.php`） | **実際に到達した経路**で出た警告・非推奨・Fatal | 到達しなかった経路（出ないことは安全の証明ではない） |
| 移行元/移行先の出力 diff | 無警告で結果だけが変わる類型（`breaking-changes.md` §7-a） | — |

**どのゲートも単独では網羅しない。** あるゲートを外すときは、その守備範囲を**どのゲートが引き受けたか**を必ず明記する（§4）。

## §2 identifier × 型の分かり具合 の下限 level

**1次元の表（identifier → 下限 level）は成立しない。** 同一 identifier でも下限は**型の分かり具合**で2〜3段動く。以下は `scripts/probe-phpstan-levels.sh` の出力をそのまま貼ったものである。

掲載値は「**なぜ最大 level が必要か**」を示す参考値であり、運用上の閾値ではない。

運用判断の根拠は、プロジェクトごとに `scripts/probe-phpstan-levels.sh` を実行した出力とする。

**この表の最小値を運用閾値にしてはならない。運用閾値は最大値側（implicit mixed 列）で決める。**
レガシーコードは型注釈を持たないため、実コードの下限は常に右端の列である。

| identifier | 確定型 | union | explicit mixed | implicit mixed |
|---|---|---|---|---|
| `argument.type` | 5 | 8 | 9 | 10 |
| `cast.string` | 2 | 7 | 9 | 10 |
| `echo.nonString` | 2 | 7 | 9 | 10 |
| `equal.alwaysFalse` | 4 | — | — | — |
| `foreach.nonIterable` | 3 | 7 | 9 | 10 |
| `method.staticCall` | 0 | — | — | — |
| `offsetAccess.invalidOffset` | 3 | 7 | 9 | 10 |
| `offsetAccess.nonOffsetAccessible` | 3 | 7 | 9 | 10 |
| `offsetAccess.notFound` | 3 | 3 | — | — |
| `property.nonObject` | 2 | 7 | 9 | 10 |
| `property.notFound` | 2 | — | — | — |
| `variable.undefined` | 0 | — | — | — |

型の分かり具合の軸を持たない類型・派生形:

| identifier | 変種 | 下限 level |
|---|---|---|
| `offsetAccess.notFound` | 入れ子（外側キーが欠ける） | 3 |
| `offsetAccess.invalidOffset` | float 添字 | 3 |
| `variable.undefined` | 条件分岐の中だけで代入 | 1 |
| `encapsedStringPart.nonString` | 文字列補間内 | 2 |
| `property.notFound` | 動的プロパティへの**書き込み** | 2 |

**測定条件**

| 項目 | 値 |
|---|---|
| PHPStan | 2.2.6（最大 level は **10**。level 11 は存在しない） |
| `phpVersion` | 80300（`--php-version=8.3`） |
| 走査 level 範囲 | 0〜10 総当たり |
| stub 構成 | **なし**（検体自身の PHPDoc から型を作る。プロジェクト非依存） |
| 検体 | `scripts/probes/phpstan/`（マーカー 39 件） |
| 実測日 | 2026-08-05 |

**この表から読むべきこと:** (1) `array\|false` を返す関数に**型注釈があれば** level 7 で捕まるが、**型注釈が無ければ level 10 まで黙る**。レガシーコードはまさに後者の形をしている。(2) `offsetAccess.notFound`（「そのキーは無い」）は **mixed に対しては存在しない** —— 形状が分かる型にしか成立せず、mixed では `offsetAccess.nonOffsetAccessible` に化ける。(3) `equal.alwaysFalse` は**両辺の型が静的に確定する場合しか出ない**。DB・外部入力由来の mixed には原理的に無力であり、`in_array()` の第3引数なし呼び出しは**一切検出できない**（`breaking-changes.md` §7 が引き受ける）。

**level を上げるコストは解析時間ではない。** 実測では level 5 → 10 で解析時間・メモリはほぼ不変（差 2% 未満）。障壁は**報告件数の増加と、それを人手で仕分けるコスト**である。したがって対策は「level を下げる」ではなく「**level は最大にし、判定対象を identifier で絞る**」が正しい。

## §3 level を上げたときのノイズ分離

level を上げると、PHP バージョンと無関係な指摘（型宣言の不足など）が混ざる。**この分離をどうやるかで、ゲートが運用に耐えるかが決まる。**

| 観点 | 案1 jq フィルタ + ゲートスクリプト | 案2 `ignoreErrors` に `identifier:` | 案3 移行専用 neon |
|---|---|---|---|
| 設定汚染 | **無し** | ノイズ抑止が恒久的に neon へ残り、移行完了後に消し忘れる | neon が2本。`paths`/`excludePaths` の二重管理が起きる |
| CI 適合性 | **終了コードを 0/1/2 で自前定義できる** | **不可**。解析ツールの exit 1 は「違反」と「実行不能」を区別しない | 案2 と同じ |
| ノイズ側の未マッチ | フィルタ結果の diff で追える | **自壊する。** ノイズが一掃された瞬間（＝望ましい状態）に未マッチで FAIL する | 案2 と同じ |
| 「未仕分け0件」を表現できるか | **できる**（台帳を外部入力として差し引ける） | **できない** | 案2 と同じ |

**案1 を単独推奨とする。** 理由は好みではない。

1. **案2・案3 は「未仕分け0件」ゲートと同時に成立しない。** 仕分け済みを機械可読に表現する手段が neon 内には `ignoreErrors` / baseline しかなく、そこへ PHP バージョン起因の identifier を入れることは禁止しているため。
2. どの案でもラッパーは必要なので、**案1 の追加コストは実質ゼロ**である。

**案2 の限定採用**: PHP バージョンとまったく無関係なノイズ（型宣言不足など）に限り `ignoreErrors` の `identifier:` 指定で抑止してよい。目的は CI ではなく**対話実行時に出力が読めること**。

| 禁止事項 | 理由 |
|---|---|
| PHP バージョン起因の identifier を `ignoreErrors` / baseline へ入れる | 検出そのものを消す。ゲートが緑になるだけで欠陥は残る |
| `identifier` 単独指定（`path` なし）で抑止する | **将来の実バグまで恒久的に沈黙する** |
| プロジェクトに 1 件も存在しない identifier を書く | 未マッチ報告で FAIL する（実測確認済み） |
| 型宣言不足の抑止を「ノイズだから」で片づける | 型宣言不足は implicit mixed の温床であり、**最大 level の検出力を自ら捨てることになる**。「1段下では ノイズ、最大 level では前提条件」と両論を書く |

## §4 ゲート採否のプローブ検証

**そのゲートが既知の非互換を実際に検出できるかを、能動的に確かめてから採用する。** バージョン番号で判断しない。`scripts/verify-gate.sh` が3値で判定する。

| 結果 | 意味 | 振る舞い |
|---|---|---|
| **VERIFIED** | 期待した全項目を期待した重大度で検出 | ゲートとして採用。以後の 0 件は `PASS` と表記してよい |
| **DEGRADED** | 一部のみ検出、または重大度が期待より低い（ERROR 期待 → WARNING） | **Fatal ゲートから外す。** 0 件は `SKIPPED (degraded)` |
| **BLIND** | 期待項目を1つも検出しない | **ゲートとして採用しない。** 0 件は `NOT-RUN` |

**外したら、必ず穴埋めの担当を決める。** DEGRADED / BLIND のときは、(1) 「どの範囲は検出できたか」を明記した表を成果物に残し、(2) Fatal ゲートの一覧から当該ツールを外し、(3) **穴埋めの担当ゲートを明示し**（削除 API → PHPStan の `function.notFound` ／ 対象バージョン実機での `php -l`。非推奨 API → 実行時ログの E_DEPRECATED。構文変更 → 対象バージョンのバイナリでの `php -l`）、(4) **穴埋めゲートが VERIFIED であることを確認する**（穴埋め先も未検証なら BLOCK）。報告には「ツール名 / バージョン / 判定 / 穴埋め先」を1行で記載する。

**(3) が最重要である。** 「外す」だけで終わると、守備範囲に穴が開いたまま「全ゲート緑」になる。

**実測例（WordPress + ACF のプロジェクト、2026-08-05）**: PHPCompatibility 9.3.5 を `testVersion 8.3` で検証したところ、期待9項目のうち検出できたのは3項目のみで、しかもすべて期待した ERROR ではなく WARNING だった（`create_function()` / `money_format()` / `each()` を「7.2 / 7.4 で deprecated」としか認識せず、8.0 での削除を ERROR にしない。`FILTER_SANITIZE_STRING` / `strftime()` / `utf8_encode()` / `utf8_decode()` / `"${var}"` 補間は**完全に未検出**）。判定は **DEGRADED**。`ignore_warnings_on_exit` 運用の下では、この状態で**終了コードが常に 0 になる**。

**`--gate=phpstan` の固有価値**: 「`excludePaths` がスコープを黙って潰していないか」を検出できる**唯一の手段**である。件数を見るだけでは「9割除外されているが1割は解析されている」状態を拾えない。**対象内へ実際に検体を植えることでしか捕まらない。**

## §5 「0 件」の解釈と、格下げの許容条件

> **「0 件」は、そのゲートがプローブによる自己検証に合格していない限り、合格として扱ってはならない。** 検証されていないゲートの 0 件は **NOT-RUN と同義**であり、報告では `SKIPPED (unverified)` と表記する。**`PASS` と書かない。**

**0 件を見たら、まず次を疑う。**

| # | 疑い | 確認方法 |
|---|---|---|
| 1 | 感度が足りない（下限 level を満たしていない） | §2 の表と、プロジェクトでの `scripts/probe-phpstan-levels.sh` の出力 |
| 2 | 守備範囲の外 | §1 の表 |
| 3 | 前提が欠けている（stub / bootstrapFiles） | 対象 API の型が mixed に落ちていないか。stub を外して件数が変わらなければ、stub は効いていない |
| 4 | スコープが潰されている | `scripts/verify-gate.sh --gate=phpstan --plant-dir=<対象内>` |
| 5 | 抑止されている | `ignoreErrors` / baseline に入っていないか |

**4点すべてを否定できて初めて「ツールの原理的限界」と記録してよい。** 実行時ログで出た欠陥が静的解析で出なかったとき、設定を疑わずに「ツールの限界」と結論づけるのは典型的な誤りである。

**レビュー対象を「0 件だったから」で絞らない。** 静的解析の件数が 0 でも、そのカテゴリの目視レビューを飛ばさない。件数はスコープの決定に使ってよいが、**スコープから外す根拠には使えない**。

> **実例（スコープ縮小による見落とし）**: ある移行で、影響ファイルを「影響が大きそうな ~10 ファイル」の名指しリストへ絞った。結果、そのリストから漏れたファイル内の入れ子配列アクセス（`$data[$key]['x']` で外側キーが特定レコードでだけ欠けるパターン）の E_WARNING を、実データでバッチ処理を動かすまで検出できなかった。`grep` や件数カウントを「すでに対象と決めたサブセット」にだけ回すと、**そのサブセット外の同型バグは件数にすら現れず、丸ごと見落とす**。
>
> 「影響が大きそうな順」に並べるのはよいが、並べた下位を**スコープから外す**のは別問題である。人手レビューは **allowlist（対象を数個選ぶ）ではなく denylist（全ファイルを候補に置き、除外するファイルは除外理由を記録する）** で進める。

## §6 ゲート結果の報告

作業完了時の報告に、次のブロックを**必ず含める**。

```
## 静的ゲートの結果

| ゲート | バージョン | 自己検証 | 設定 | 結果 |
|---|---|---|---|---|
| PHPStan | 2.2.6 | VERIFIED (4/4) | level 9 / phpVersion 80300 / stubs: acf-pro, wp-cli | PASS |
| PHPCompatibility | 9.3.5 | DEGRADED (0/9) | testVersion 8.3 | SKIPPED (degraded) |

**有効 identifier**: offsetAccess.* / property.nonObject / property.notFound / foreach.nonIterable / variable.undefined
**除外 identifier と理由**: missingType.*（型宣言不足。ランタイム挙動と無関係。201 件）
                            argument.type（メッセージ二次フィルタ未整備のため第2段へ繰り延べ。149 件）
**PHPCompatibility の穴を埋めたゲート**: 削除API → PHPStan function.notFound ／ 非推奨API → 実行時ログ
**観測 18 件 / 仕分け済み 18 件 / 未仕分け 0 件**
```

結果は4値で表記する。`PASS`（VERIFIED かつ未仕分け 0 件）／ `FAIL`（未仕分けが1件以上）／ `SKIPPED (degraded)`（DEGRADED。検出できた範囲を明記する）／ `SKIPPED (unverified)`（自己検証を未実施）／ `NOT-RUN`（BLIND または未実行）。**`PASS` 以外はすべて合格ではない。**

**level と、有効／除外 identifier を必ず併記する。** どの強度で測ったかが伝わらない報告は、次の担当者に「全部見た」と誤読される。

## §7 修正後の再走査と baseline 保守

**件数の増減で判定しない。行単位の差分で判定する。** 件数が同じでも中身が入れ替わっていることがある（`is_array()` ガードを足して「オフセットアクセス不可」が1件減り「オフセットの型が不正」が1件増える、など）。

```bash
./scripts/phpstan-gate.sh --format=tsv > before.txt   # 修正前
# ... 修正 ...
./scripts/phpstan-gate.sh --format=tsv > after.txt    # 修正後
diff -u before.txt after.txt   # '+' 行が1本でもあれば新規指摘
```

**JSON を正、人間向けの表を副とする。** 表形式は折り返し・省略が入り diff に使えない。成果物・差分基準は JSON 経由の正規化テキストに固定する。

**再走査は速い。** 結果キャッシュ（`tmpDir`）が効いていれば全体再走査は 1 秒未満で回る（実測: コールド 6.3 秒 → ウォーム 0.67 秒。約 9 倍）。`tmpDir` を明示指定して `.gitignore` へ入れること。キャッシュ破棄は `phpstan clear-result-cache -c <config>` を使い、**`rm -rf` をスクリプトに書かない**。

**baseline の保守**: (M1) `count:` を書かないエントリを推奨する —— 修正のたびに count がずれる問題が構造的に消える。**ただし「同じファイルで同型の指摘が新たに増えても気づけない」トレードオフがある**。(M2) `count:` を残す運用なら**修正コミットに baseline 更新を同梱する**（別コミットにすると CI が赤いまま放置される）。(M3) **baseline は level とセットで有効**であり、先頭コメントに生成時の level とツールのバージョンを記録する（実測では、ある baseline は level 4 以上で全マッチしたが level 0 では 8 件が未マッチだった）。(M4) **`--generate-baseline` で丸ごと再生成しない**。再生成すると PHP バージョン起因の実バグまで baseline に入る。手で1エントリずつ足す。

**未マッチ報告（`reportUnmatchedIgnoredErrors`）は `true` のままにする。** `false` にすると baseline の陳腐化が**検出されなくなり**、「消えたはずの指摘が実は消えていない／消えた指摘の baseline が残り続ける」状態が静かに蓄積する。FAIL するのは正しい振る舞いであり、**うるさいから消す、をしない**。ただし原因種別が違うので `MAINTENANCE` として区別表示する。
