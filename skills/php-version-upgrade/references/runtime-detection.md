# 実行時検出 — 到達した経路で実際に何が出るか

静的解析は「到達しうる欠陥」を、実行時ログは「**実際に到達した経路で出た欠陥**」を捕まえる。両者は代替関係ではない。

**実行時ログに出なかったことは、その箇所が安全であることを意味しない。** 到達しなかっただけかもしれない。逆に、実行時に出て静的解析が沈黙した箇所は、**ツールの限界ではなく設定の不足**であることが多い（§3）。

---

## 設置しないという選択肢を先に検討する

移行専用ロガーは、**本番／ステージングで動く、素性の分からないハンドラをアプリの最下層に挿す**行為である。恒久的なリスクを負う前に、負わない道を検討する。

| 状況 | 判断 |
|---|---|
| 本番で `display_errors=Off` かつ `error_log` が docroot 外で機能している | **標準のエラーログを収集するだけで足りることが多い。ロガーを入れない。** |
| 自社コードのフレーム分離が必要（他社プラグインのノイズに埋もれる） | ロガーを入れる |
| 実行コンテキスト（cron / REST / AJAX）の判別が必要 | ロガーを入れる |
| 同一箇所の大量出力でログが読めない | ロガーを入れる（重複抑制が要る） |

**環境設定の実確認（§4）は、ロガー設置より前に行う。** ロガーを設置すると環境の実設定が観測できなくなる。

## §1 設置

| 手段 | 捕捉範囲 | 難易度 |
|---|---|---|
| `auto_prepend_file` | リクエスト最初期から全域 | 高 |
| アプリ最下層での `require` | フレームワーク初期化のほぼ全域 | 中 |
| フレームワークのドロップイン機構 | その機構がロードされて以降 | 低 |

**ドロップイン機構は「ロードされる前の区間を捕捉できない」ことを必ず明記する。** 黙っておくと、また「0 件＝安全」の誤読が起きる。WordPress 固有の設置手順と限界は `references/wordpress-notes.md` を参照する。

**設定は「定数 → 環境変数 → 既定」の順に解決する。**

| 設定名 | 既定 | 注意 |
|---|---|---|
| `PHP_MIGRATION_LOG` | `sys_get_temp_dir()/php-migration.log` | **docroot 内を既定にしない** |
| `PHP_MIGRATION_ROOT` | `getcwd()` | ログ内パスの基準。**静的解析との突合の要** |
| `PHP_MIGRATION_OWN_PATHS` | 無し（実質必須） | **未設定なら `own:<unconfigured>` を出力する。推測で埋めない** |
| `PHP_MIGRATION_EXCLUDE_PATHS` | `/vendor/` | 自社コードから除外する部分文字列 |
| `PHP_MIGRATION_DEDUP` | `1` | 同一キーを何回まで即時出力するか |
| `PHP_MIGRATION_BOOT_LOG` | `1` | 高トラフィックの Web では `0`。ただし §2 の判定に影響する |
| `PHP_MIGRATION_MAX_UNIQUE` | `200` | 1リクエストのユニーク件数上限。超過は `truncated:1` で記録する |
| `PHP_MIGRATION_EXPIRE` | 無し（**必須**） | 自己失効日。期限を過ぎたらハンドラを登録しない |

**`OWN_PATHS` 未設定時に推測で既定を埋めない。** 誤った `own` は「他社コード由来だから無視」という判断を誘発し、**検出漏れそのものになる**。

**出力先の規定**

| 規定 | 理由 |
|---|---|
| **既定の出力先は docroot 外** | 多くのフレームワークの既定ログパスは Web 配信対象の内側にある |
| docroot 外に置けない場合は、**設置直後に `curl -I <URL>` で 403/404 を確認するまで有効化しない** | 「置けないから中に置いた」で終わると恒久的な情報公開になる |
| ファイル名にランダム要素を入れない | Security by obscurity。ディレクトリリスティングやバックアップ経由で漏れる |
| 出力先はコード内にハードコードせず、定数／環境変数で外から与える | ハードコードすると「動く場所に置く」ために docroot 内へ寄っていく |
| ディレクトリは `0750`、ファイルは作成時に明示的に `chmod 0640` | 追記系の書き込みは **umask 依存で 0644 になりうる** |
| **ディレクトリに空の `index.html` を置かない** | それは docroot 内に置いてしまった場合の弥縫策であり、docroot 外に置く規定と両立しない。**「置いたら弥縫策を考える」導線をつくらない** |

**ログに書かないもの（最重要）** — 本ロガーは「どこで警告が出たか」を知るためのものであって、「何が入っていたか」を知るためのものではない。**両者を分けないと、専用ログが個人情報の複製になる。**

| 書く | 書かない |
|---|---|
| errno / errstr（PHP が生成する固定文言） | `$_POST` / `$_GET` / `$_REQUEST` の**値** |
| errfile / errline | `$_COOKIE` / `Authorization` ヘッダ / セッション ID |
| 自社コードのフレーム（`own=file:line`） | **関数呼び出しの引数値** |
| 実行コンテキスト | 顧客 ID / 会員番号 / メールアドレス / 氏名 / 住所 / カード関連の一切 |
| リクエストの**パス部分のみ** | クエリ文字列（トークン・メールアドレスが載る）／ User-Agent / IP |

`errstr` 自体に値が載る類型がある（`A non-numeric value` 系や TypeError は値の一部を含む）ため、**512 バイトで切る**。設置前にステージングで最低1周分の実ログを目視確認する。

## §2 ログの読み方と集計

1行1レコードの LTSV（`label:value` をタブ区切り）である。`grep` / `awk` / `cut` がそのまま使え、途中で切れた行が後続行を壊さない。

| フィールド | 内容 |
|---|---|
| `lv` | `E_WARNING` / `E_DEPRECATED` / `E_NOTICE` / `E_ERROR` / `BOOT` / `DEDUP` / `HINT` |
| `ctx` | `web` / `cron` / `ajax` / `rest` / `cli` / `admin` |
| `sup` | `@` 抑制なら `1` |
| `own` | 自社コード最深フレーム `相対パス:行`。不明時 `<none>` / `<unconfigured>` |
| `depth` | `own` がエラー発生位置から何フレーム外か |
| `at` | `$errfile:$errline` の相対パス。**静的解析との突合の主キー** |

集計は `scripts/aggregate-migration-log.sh` を使う。既定の集計軸は `own`（自社コードの箇所ごと＝修正単位）。

| 状況 | 出力 | 終了コード |
|---|---|---|
| BOOT 行あり・エラー行 1件以上 | 集計表 | `0` |
| BOOT 行あり・エラー行 0 件 | `[OK] N 回の実行で警告 0 件。ロガーは起動していました` | `0` |
| **BOOT 行なし・エラー行 0 件** | `[NG] ロガーの起動記録がありません。「0件＝安全」と解釈しないでください` | **`2`** |
| BOOT 行なし・エラー行あり | BOOT ログを切って運用された可能性を注記して集計 | `0` |

BOOT 行なしを `1` ではなく **`2`** にするのは、これが「違反」ではなく**判定不能**だからである。

**件数は「プロセス内の重複抑制後」の値である。** 1リクエストで同じ箇所を何度踏んでも1行に畳まれる（実例: 同一箇所を 302 回踏んだケースが 1 行になる）。ただし**呼び出し元が違えば別行になる** —— 共有ヘルパの同一行が別々の呼び出し元から踏まれるのは別々の欠陥だからである。

**重複抑制のスコープはプロセス内（1リクエスト / 1 CLI 実行）に限る。** プロセス横断の集約は集計スクリプトの仕事である。

## §3 静的解析との突合

`scripts/correlate-static-runtime.sh` を使う。**主キーは `file:line`。** `message` は文言が一致せず、`identifier` は実行時側に存在しない（errno しか無く、N:M で逆写像できない）。

`file:line` はコードが変わると壊れるため、**`--rev=<sha>` を必須引数とし、現在の HEAD と照合する。不一致なら `exit 2`。黙って進めない。**

出力は3区分:

```
[A] 実行時に出て、静的解析も検出した ............ ゲートは機能している
[B] 実行時に出たが、静的解析は沈黙 ............... ★要調査
[C] 静的解析は検出したが、実行時には出なかった ... 偽陽性候補 / 未到達経路（仕分けの入力）
```

**区分 B は、ツールの限界と結論づける前に必ず次の4点を確認する。**

1. そのカテゴリの下限 level を満たしているか（`detection-gates.md` §2）
2. そのゲートの守備範囲か（同 §1）
3. 必要な stub / bootstrapFiles が入っているか（入っていないと型が mixed に落ちる）
4. `ignoreErrors` / baseline に入っていないか

**区分 B が 0 件でも「0 件だった」と出力する。** 空の場合に何も出さないと、実施したか未実施かが区別できない。

**区分 C を「実行時に出ないから偽陽性」と即断しない。** 未到達経路の可能性がある。判定根拠は「到達不能であることを示す」か「実測で示す」のいずれかで書く（`triage-ledger.md` §1）。

**パス正規化の不一致は実務で必ず一度は踏む。** 区分 A も C も 0 件で B だけが大量になったら、`PHP_MIGRATION_ROOT` と `--root` が同じディレクトリを指しているかを確認する（突合スクリプトがこの状況を検出して警告する）。

## §4 移行先環境のエラー表示・ログ設定の実確認

**推測せず、必ず実測する。**「フレームワークが本番では出さないようにしているはず」は成り立たない。

**確認は「php.ini の値」ではなく「実際のリクエストが見る値」で行う。** php-fpm のプール設定・`.htaccess` の `php_value`・`.user.ini`・フレームワークの `ini_set` が重なるため、CLI の `php -i` は答えにならない。

| # | 項目 | 確認手段 | 合格条件 |
|---|---|---|---|
| S1 | Web リクエスト実効の `display_errors` | フレームワーク読込後に走る一時ドロップインで `ini_get()` を**ログへ**出す。**画面には出さない** | `Off` |
| S2 | 同 `display_startup_errors` | 同上 | `Off` |
| S3 | 同 `error_reporting`（数値） | 同上 | 移行期は E_WARNING / E_DEPRECATED を**含める**（ログ収集のため）。ただし S1 が Off |
| S4 | `log_errors` と `error_log` の実パス | 同上 | `log_errors=On`、出力先が **docroot 外** |
| S5 | エラーログが Web から取得できないか | **実際に HTTP で叩く**（`curl -I <site>/<path>`） | 403 / 404 |
| S6 | フレームワークのデバッグ定数の実値 | 設定ファイルを読む | 本番はデバッグ表示 off。**既定のログパスを使わない** |
| S7 | `zend.exception_ignore_args` | S1 と同時に取得 | `On`（Off だとスタックトレースに引数値＝機微情報が載る） |
| S8 | 非 HTML 出力経路（CSV/Excel/JSON/画像/ダウンロード）で警告が本文へ混入していないか | 対象バージョンで実データ実行し、**出力ファイルの先頭バイトを目視**（`head -c 200 out.csv`） | BOM / 期待ヘッダで始まる |
| S9 | エラー画面／混入警告に絶対パス・DB 情報・引数値が出ていないか | S8 のサンプルと、意図的に警告を起こしたステージングのページ | 出ない |

**移行前（`--from` 環境）と移行後（`--to` 環境）の両方で取得し、差分を成果物に残す。** 移行前の値を記録していないと、移行後に見つけた設定が「元からそうだった」のか「移行で変わった」のかを判別できず、是正の緊急度を誤る。

**是正**

| 状況 | 是正 | 注意 |
|---|---|---|
| `display_errors=On` を発見 | **即座に Off。** ただし同時に `log_errors=On` と docroot 外の `error_log` を設定してから落とす | Off にするだけだと**警告が完全に見えなくなり、移行の残問題を検知する手段を失う**。「露出を止める」と「観測をやめる」を混同しない |
| ログが docroot 内 | 出力先を docroot 外へ移す。移動できないなら Web サーバで拒否設定を入れ、**`curl` で 403 を確認**（S5） | 「実在ファイルは rewrite されず直接配信される」書き換えルールは一般的である。**置けば取得可能**と考える |
| 既に露出していた期間がある | 露出内容の範囲（絶対パス／DB 名／引数値／メールアドレス等）を評価し、必要なら通知・パス変更を検討 | 「Off にしたから終わり」にしない |

**環境確認（S1〜S9）とロガーの `display_errors=0` 強制は目的が違う。** 環境確認の目的は「**情報露出の停止**」（対象は php.ini / サーバ設定であり恒久的）、ロガーの強制の目的は「**出力破損の防止**」（対象は当該リクエストのみで移行期間限定）。**両者は独立であり、ロガーを入れたから環境確認は不要、にはならない。** 逆に環境が Off でも、ステージングで On のことがあるため自衛として残す。

## §5 本番ホストで実行してよいコマンド

**対象ファイルは denylist、本番で叩くコマンドは allowlist。** この対比で覚える。

| 許可（読み取りのみ） | 禁止 |
|---|---|
| `php -v` / `php -i` / `php -l <file>` | `rector process`（`--dry-run` なし）— **ソースをその場で書き換える** |
| `tail` / `grep` によるログ閲覧 | `phpcbf` — **自動整形でソースを書き換える** |
| `curl -I` によるログ到達性の確認 | `phpstan analyse` — `bootstrapFiles` は **`require` される**ため副作用が走りうる。CPU/メモリも占有する |
| ロガーの設置・撤去 | `git checkout <branch>` — 本番ディレクトリでブランチを切り替えない |

**実データでの cron / バッチ手動実行が最大のリスクである。** メール送信・決済 API 呼び出し・外部連携が**実際に走る**。

1. 実データ実行は**ステージング＋本番データのコピー**を既定とする。
2. 本番で避けられない場合は、**外部送信をブロックする手段（メール・決済のサンドボックス切替）を先に確認する。**
3. 冪等でない処理は実行しない。

**「実データで流せ」だけを書いて送信抑止に触れない指示は危険である。** 必ず対で書く。

## §6 撤去 — 「削除」ではなく「不在の検証」で完了する

撤去漏れ＝本番に恒久的なエラーハンドラと個人情報予備軍のログが残る。

| # | 手順 | 検証 |
|---|---|---|
| 1 | 設置と同時に撤去チケットを起票し、ファイル先頭に `// 撤去期限: YYYY-MM-DD / 起票: <ID>` を書く | ファイルを読むだけで期限が分かる |
| 2 | **自己失効を実装する**（`PHP_MIGRATION_EXPIRE`）。期限を過ぎたらハンドラを登録せずに抜ける | 撤去を忘れても機能が止まる（フェイルセーフ） |
| 3 | バージョン識別子を持たせ、**ステージング限定**で `X-Migration-Logger: <ver>` を返す | 外形監視で残存を検知できる |
| 4 | ファイル削除 → **本番に無いことを確認**する | 「デプロイした」ではなく「本番に無い」を確認する |
| 5 | 収集済みログの**退避と削除** | ログ自体が撤去対象 |
| 6 | 撤去後に S1〜S5 を**再実行** | ロガーが `ini_set` していた値が元へ戻ることを確認 |
| 7 | 撤去記録をフィードバック工程の成果物に含める | 「実施した」ことを後から検証可能にする |
