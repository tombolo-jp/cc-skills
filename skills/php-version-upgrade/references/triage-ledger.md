# 仕分け台帳 — 全件を列挙し、1件ずつ判定と根拠を書き、未判定を残さない

移行作業で「全件を洗い出して1件ずつ判定する」工程はいくつも現れる。それらは**同一のデータモデル**を持つ。書式を1箇所で定義し、機械判定を共通化する。

**ゲートは「件数 0」ではなく「未仕分け 0 件」で定義する。** 件数は欠陥数ではない（実測例では 46 件の指摘のうち 14 件が偽陽性だった）。件数を合格条件にすると、件数を減らすために抑止するインセンティブが生まれる。

| 台帳 | `kind` | 対応する工程 |
|---|---|---|
| §2 静的解析の仕分け | `phpstan-triage` | 静的解析の指摘を1件ずつ判定する |
| §3 棚卸し（grep 由来） | `grep-inventory` | 機械検出できない類型を grep で列挙して判定する |
| §4 ブランチ間突合 | `branch-diff` | 複数ブランチ間の差分を「意図した方針差」と「適用漏れ」に仕分ける |
| §5 対象ファイル台帳 | `scope` | 解析対象から除外したファイルと、その除外理由を残す |
| §6 フィードバック突合 | `feedback` | 移行後に見つかった欠陥を「なぜゲートが取りこぼしたか」で分類する |

---

## §1 台帳共通規約

```markdown
# <台帳名>

<!-- ledger:meta v1 -->
| キー | 値 |
|---|---|
| kind | phpstan-triage |
| tool | phpstan 2.2.6 |
| level | 9 |
| phpVersion | 80300 |
| identifiers | bin/php8-identifiers.txt |
| stubs | php-stubs/acf-pro-stubs, php-stubs/wp-cli-stubs |
| paths | wp-content/plugins/my-plugin, wp-content/themes/my-theme |
| judged_at | 2026-08-05 |
<!-- /ledger:meta -->

<!-- ledger:rows v1 -->
| 状態 | path | identifier | message | count | 根拠種別 | 判定根拠 | 判定関与 | 外部入力起点 | 参考行 |
|---|---|---|---|---|---|---|---|---|---|
<!-- /ledger:rows -->
```

| 規約 | 内容 |
|---|---|
| フェンス | `<!-- ledger:meta v1 -->` / `<!-- ledger:rows v1 -->` の HTML コメントで囲む。**機械判定はフェンス内のみを読む**。見出しの改名や章立ての変更でパーサが壊れない |
| バージョン | フェンスに `v1`。未知バージョンは `exit 2`（判定不能） |
| セル内の `\|` | `\|` へエスケープする。パーサは「直前が `\` でない `\|`」で分割し、その後アンエスケープする。**`array\|false` は message に必ず出る** |
| `path` | **リポジトリルート相対**・`/` 区切り。解析ツールの出力は絶対パスなので、突合側で解析ルートを剥がす |
| 状態 enum | `未判定` / `対応済` / `偽陽性` / `保留`。**`未判定` は必須語**（行だけ足して通す抜け道を塞ぐ） |
| 根拠種別 enum | `到達不能` / `実測` / `仕様` / `—` |
| 空欄禁止 | `判定根拠` が空、または **20 文字未満**の行は、`状態` の値によらず**未仕分け扱い**。`偽陽性` なら書式エラーとして `exit 2` |

**「未判定」を偽陽性へ倒さない。** 読んでも安全か分からない場合は `未判定` のまま残し、ゲートを FAIL のままにしてエスカレーションする。判定不能であること自体が成果物である。

**台帳は測定条件とセットでしか意味を持たない。** `meta` の `level` / `phpVersion` / `identifiers` / `paths` が実行時の条件と一致しない場合、ゲートは合否を出さず `exit 2` を返す。低い感度で作られた台帳が高い感度の走査に対して「全件仕分け済み」として通れば、**「弱い設定で 0 件だったから問題なし」という誤りが、台帳という新しい皮をかぶって再発する。**

## §2 静的解析の仕分け台帳（`kind: phpstan-triage`）

**fingerprint（キー）= `path` + `identifier` + `正規化した message`。行番号はキーに含めない。**

| 判断 | 理由 |
|---|---|
| **行番号をキーにしない** | 実測で、32 件の修正により台帳の行番号が最大 10 行ずれていた。行番号をキーにすると、無関係な行の追加ひとつで全エントリが無効化される。台帳は次回移行まで生き残る資産である |
| **`message` は原文全文**（短縮・要約禁止） | 短縮するとツール出力と文字列一致せず突合不能になる |
| **`message` を正規化する** | 型の詳細（`array{x: 1}` のような具体値）を `array{...}` へ潰す。型推論が変わると message の型表記が変わるため |
| **`count` はキーに含めず、通知にのみ使う** | 増加は NOTICE、減少は WARN。**どちらも FAIL にしない**（baseline の回数不一致で CI が赤いまま放置される問題を台帳側で再現しない） |
| **`identifier` を必須列にする** | ホワイトリスト照合ができなくなるため |

**正規化規則**（両側に同一適用する。**ここがズレると全件が未仕分けに落ちる**）:

| 項目 | 規則 |
|---|---|
| パス | 絶対パスを `realpath` で解決し、解析ルートからの相対へ。区切りは `/` |
| identifier | 前後空白の除去のみ |
| message | 前後空白を除去。内部の連続空白を1個へ畳む。末尾 `.` は保持。型の具体値を `{...}` へ潰す |
| 台帳側 | 追加でバッククォート除去、`\|` → `|` アンエスケープ、`**強調**` の除去 |

**同一 fingerprint で判定が分かれる場合**: 同一 fingerprint の行を複数書き、`count` の合計を検出数に一致させる（`参考行` で人間が区別する）。または判定根拠欄に「L412 のみ実バグ。L88 は到達不能」と書いて1行で両方を説明する。

**セキュリティ由来の追加列**

| 列 | 値域 | 目的 |
|---|---|---|
| `判定関与` | `Y` / `N` | `Y` の行は**安全側（拒否・中断）に倒すことを必須**とし、判定根拠に「fail-closed であること」を書く。「値が無いかもしれない」という指摘を消すためのガードが、**認可分岐を丸ごとスキップさせる**事故を防ぐ |
| `外部入力起点` | `Y` / `N` | `Y` なら、PHP バージョンの警告とは独立に「その値に対する認可・型・範囲の検査が存在するか」を1行で判定する |

> **移行作業は事実上のセキュリティレビュー機会である。** 感度を上げると外部入力に触る箇所が自動的に洗い出される。その機会を捨てるのは損失だが、移行のスコープを勝手に広げるのも誤りである。だから「**直さないが記録する**」に固定する。
>
> 検査が存在しなければ「移行スコープ外の別課題」として台帳に記録し、担当者へエスカレーションする。**移行作業のついでに直さない**（挙動変更になる）。**記録せずに素通りさせない。**

**修正時に持ち込みやすい誤り**（`判定関与` / `外部入力起点` が `Y` の行では特に確認する）:

| # | 誤り | 規定 |
|---|---|---|
| A1 | フェイルオープンなガードの混入 | 指摘は「値が無いかもしれない」であって「無いときどうすべきか」は教えない。**認可・権限チェックを含む分岐をガードで飛ばさない** |
| A2 | `??` のフォールバックが認可の既定値になる | **権限・種別・フラグの `??` 既定値は、必ず最も権限の低い値／不許可側にする** |
| A3 | キャストによる検証の骨抜き | **比較演算子を緩める方向の修正を禁止する。`===` は `===` のまま、型を合わせるのは値の生成側で行う** |
| A4 | 広域抑止への逃避 | PHP バージョン起因 identifier の `identifier` 単独指定（`path` なし）を禁止する。抑止するなら `path` を伴わせ、台帳と1対1にする |
| A5 | 台帳が攻撃の設計図になる | 台帳は「外部入力を扱う箇所の file:line と、そこで何がガードされていないか」の一覧である。**非公開リポジトリ内に置く。** 公開リポジトリでは file:line を含めず非公開の別管理とする |

## §3 棚卸し台帳（`kind: grep-inventory`）

機械検出できない類型（比較セマンティクスの変化など）を `grep` で列挙して判定する。共通規約は §1 と同じだが、キーが異なる。

| 項目 | §2 静的解析の仕分け | §3 棚卸し |
|---|---|---|
| 検出源 | 解析ツールの JSON | `grep -nE` の結果（`meta.pattern` に正規表現を記録する） |
| キー | `path` + `identifier` + `message` | `path` + `正規化断片` + `連番` |
| `正規化断片` | — | 該当行のソース断片。前後空白を除去し連続空白を1つに畳む |
| `count` | 必須 | 使わない（1行＝1箇所） |
| 状態 enum | `未判定`/`対応済`/`偽陽性`/`保留` | `未判定`/`安全`/`条件付き`/`危険`/`別件`（「偽陽性」はツール指摘に対する語なので使わない） |

**機械前処理の規定**: 判定則に照らして機械的に安全と確定できる行（例: 既に厳密比較になっている行）は、自動的に `状態=安全 / 根拠種別=仕様` を埋めてよい。残りのみ人手判定に回す。「1件ずつ判定する」を守りつつ作業量を落とせる。

**「安全」判定にも必ず `判定根拠` を埋める**（ルール名でよい）。**空欄を許すと「検出ヒットなし＝問題なし」の再発になる。**

## §4 ブランチ間突合台帳（`kind: branch-diff`）

複数ブランチを並行して移行する場合、**方針が違っても実バグ修正はどのブランチにも等しく必要**である。

| 項目 | 内容 |
|---|---|
| キー | `path` + `ハンク連番` |
| 固有列 | `方向`（a→b / b→a）、`分類`（`意図した方針差` / `適用漏れ`）、`根拠` |
| ゲート | `git diff <a> <b> -- <src> ':(exclude)vendor'` の**全ハンク数 == 行数**、`分類` の未記入が 0 件 |

**突合の方式を固定する。** 「両ブランチで解析を再実行して結果を比べる」方式を**採らない**。再実行方式は「両方で同じように検出されない欠陥」を構造的に見逃す。`git diff` の全ハンクを1件ずつ分類する。

**双方向で各1台帳を作る。** 片方向だけだと「b にあって a に無い」修正が漏れる。

## §5 対象ファイル台帳（`kind: scope`）

denylist 原則の実体。**全ファイルを候補に置き、除外するファイルは除外理由を記録する。**

| 項目 | 内容 |
|---|---|
| キー | `path` |
| 固有列 | `区分`（`対象` / `除外`）、`除外理由`（`区分=除外` なら必須） |
| ゲート | `git ls-files '<target-paths>/*.php'` の**全件 == 行数**。総数の機械確定はこの行数一致で担保される |

**`区分=対象` の行数と見積もり時間の対応を列にしない。** 列に入れると、行を減らす動機が生まれる。工数見積もりが allowlist を固定化する構造をつくらない。

## §6 フィードバック突合台帳（`kind: feedback`）

移行後に見つかった欠陥を、**「なぜゲートが取りこぼしたか」**で分類してスキルへ還流させる。

固有列: `source` / `evidence` / `location` / `category` / `detectable_by` / `why_missed` / `verified_by` / `skill_action` / `applied`

**`why_missed` は自由記述にしない。8つのコードから選ぶ。**

| コード | 意味 | 対応先 |
|---|---|---|
| `W1-設定値誤り` | スキルが書いた閾値・設定値が誤っていた | **SKILL.md / references を即修正** |
| `W2-バージョン要件未規定` | ツールのバージョンで守備範囲が変わることを規定していなかった | **プローブへ項目追加** |
| `W3-守備範囲の誤認` | そのゲートが原理的に見ないものを、見ると思っていた | **`detection-gates.md` §1 へ追記** |
| `W4-原則の非強制` | 原則は書いてあったが、工程で強制する仕組みが無かった | **成果物要件へ追加** |
| `W5-突合方式の欠落` | 手順が方式を指定していなかった | **手順に方式を固定して書く** |
| `W6-手段の不在` | 方針だけあって実装手段が無かった | **`scripts/` に実ファイルを追加** |
| `W7-ツールの原理的限界` | どのゲートでも検出できない | **`breaking-changes.md` §7 へ追記。手順は変えない** |
| `W8-フェーズの未実施` | 前回の移行でフィードバック工程を回していなかった | **プロセス側の問題として記録** |

**W1〜W6 は「スキルの欠陥」、W7 は「世界の制約」、W8 は「運用の欠陥」。** この区別を機械的に付けさせることで、`W7` へ逃げる（＝「ツールの限界でした」で片づける）ことを抑止する。

| # | 再発検出のトリガー | 判定 |
|---|---|---|
| T1 | `why_missed` が W1〜W6 のいずれか | スキルの欠陥。`skill_action` に `対応不要` を書くことを**禁止**する |
| T2 | `verified_by` が `未検証` | その行は結論として使えない。**「検出できたはず」を検証せずに書かない** |
| T3 | 同じ `why_missed` コードが前回の突合表にも存在する | **再発。** 前回の修正が効いていない。修正内容そのものを見直す |
| T4 | `detectable_by` が `なし` の件が前回より増えている | 検出不能類型のカタログが育っていない可能性 |

**対象3種（実行時ログ / 障害報告 / 他者が手で直したコミット）それぞれについて、0 件でも「0 件だった」行を残す。** 行が1つも無い台帳は「未実施」と区別できない。
